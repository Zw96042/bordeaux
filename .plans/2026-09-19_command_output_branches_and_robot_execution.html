Branch directly on a command result. Author and preview the routes now; add robot execution through an explicit, versioned contract later.

Interaction

A command runs once with its configured inputs. Its inspector defaults to “Continue to next step.” Selecting an output under “After command completes” adds routes beneath that command. This keeps the source of the result visible and avoids a separate Conditions catalog or an ambiguous reference to another command invocation.

Named outcomeOne route per enum value, plus OtherwiseUse declared NI enum names, not inferred strings.
NumericOrdered comparisons, plus OtherwiseAdd comparisons; choose =, ≠, <, ≤, >, ≥; enter typed thresholds; move checks earlier.

The first matching route wins. Empty routes continue immediately; every route rejoins the following sibling step. Preview selects a route manually and never pretends to execute a VI or predict its result. Nested command branches work the same way. Removing populated branches or changing their command/output requires an explicit destructive confirmation.

Current GUI scope

  • NI command inspection exposes supported top-level output terminal names, labels, scalar schemas, numeric bounds, and connector terminal numbers. Command Status Info lifecycle terminals are excluded.
  • Boolean, enum, signed/unsigned numeric types are supported; large integer comparisons retain decimal strings without JavaScript rounding. Unsupported output types produce diagnostics while preserving supported inputs and outputs.
  • Saved routes carry stable IDs, a selected output name, a schema snapshot, comparisons, and nested steps. Missing or changed outputs preserve saved work and show recovery guidance. Existing condition decisions remain readable with their routes; new standalone Conditions are not offered.
  • Branch-bearing active routines fail export validation and serialization. Path-only BDX export remains independent. This change does not connect to a robot or establish command execution authority.
  • Output branching belongs to between-step routine commands. Path event output handling and migration of old conditional event gates remain future work.

Robot execution plan

  1. Version the contract. Define a new routine wire-schema capability for command result branches. Keep existing readers rejecting unsupported versions; do not silently drop branches. Include command invocation ID, output name and type, ordered routes with stable IDs, typed comparison literals, and the mandatory fallback where applicable. Include output metadata in catalog semantic identity.
  2. Bind LabVIEW outputs. Extend the team-owned dispatch adapter to return typed result values when the existing completion lifecycle reports finished. Bind using verified command identity plus terminal number/name/type; verify the VI/type fingerprints. Specify one result snapshot per invocation. Never read a prior invocation’s indicator value as the new result.
  3. Define scheduler timing. Invoke command, await completion, atomically capture its result, select exactly one route, run that route, then rejoin. Cancellation/disabled state aborts evaluation and clears pending results. Commands that never finish need an explicit timeout policy before release.
  4. Specify comparisons. Boolean and enum matching are exact; numeric order is stable and first-match. Match exact-width signed/unsigned integers without floating conversion. Reject nonfinite numeric outputs. Otherwise handles a valid unmatched value; missing output, wrong type, timeout, cancellation, and execution errors are failures, not ordinary fallback matches.
  5. Make execution observable. Report invocation ID, selected route ID, and a bounded typed result summary. The GUI can show the robot-selected route independently from its local preview. Do not reuse local preview state as execution authority.
  6. Migrate deliberately. Existing standalone predicates cannot be assumed equivalent to a command output. Provide a user-reviewed replacement that moves existing branch children to a selected output. Define event gating separately: a previous command result needs an explicit invocation reference and lifetime contract.
  7. Enable deployment after parity. Negotiate the new receiver capability, validate every route and referenced path, and only then remove the GUI export guard. Preserve explicit scoped push, immutable review, readback, and disabled-runtime acknowledgment.

Runtime acceptance criteria

  • Contract fixtures round-trip all supported NI scalar types and reject unknown versions/types, malformed routes, stale bindings, invalid references, and out-of-range literals.
  • LabVIEW scheduler tests cover both boolean routes, all enum values, valid unmatched values, overlapping numeric comparisons, exact boundary equality, negative values, and 64-bit limits.
  • Exercise nested branches, empty routes, rejoin order, repeated command invocations, stale result prevention, cancellation, disable, timeout, missing output, nonfinite output, and no robot writes during local save.
  • Replay the same fixtures in desktop preview selection and robot execution; ensure matching route IDs and step order. Verify actual Windows NI inspection and robot integration independently from mocked desktop tests.

Limits and follow-up decisions

Current GUI parses top-level scalar outputs, not cluster field paths or arbitrary string outcomes. Enums larger than 255 values are not offered because each value plus Otherwise must fit the 256-route bound. The first runtime release should specify timeout configuration and whether adapters support command results beyond LabVIEW before implementing those features.

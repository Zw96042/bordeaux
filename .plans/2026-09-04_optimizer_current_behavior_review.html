Projectbordeaux
Versionv1
Statusactive · 2026-09-04

The optimizer has useful underlying machinery, but its default search and result ownership do not deliver a dependable performance upgrade.

Verdict: repair the baseline/result contract and default search before adding more solver sophistication. This is a review and proposed work, not a claim that the feature is fixed.

Scope and evidence

Reviewed the current dirty working tree on main, whose base HEAD is e2e3ea01ee097792e8aeda8aabf769b97057f493. Many planner and UI edits predate this review; the base commit alone does not represent the reviewed code. A separate read-only Codex agent inspected solver behavior and focused tests while the primary agent traced renderer, worker, routine, and export ownership. No application files were edited.

The owner clarified that switching to Optimized briefly shows a 3.7-second path before returning to Profiled even while completely idle. The reported flicker/failing path was not reproduced in the running app. Findings below distinguish direct source behavior from failure scenarios inferred from it. Passing fixtures do not establish that the user's route is supported or that the default experience is good.

Actionable findings

1. Default search stops after one candidate — high

src/shared/planners/corridorFinal.ts:16 defines common=1, stress=24, hard=36 evaluations. The common run spends its only evaluation on the first alternating handle-length seed at lines 302–315 and cannot enter local search at line 322. App.jsx:291 requests common. This is a direct limit on product usefulness, not evidence that a stronger solver must be installed.

2. Displayed results switch by design after editing — high

src/renderer/app/App.jsx:287–304 makes each completed interactive result the visible pending result, then replaces it with final success or fallback. EditablePlaybackField additionally bridges drag previews. An edited optimized path therefore cycles through distinct geometries/timing representations. This establishes preview/final replacement but does not prove the cause of the confirmed idle reversion. Reproduce enabling optimization without any further interaction, capture the intermediate 3.7-second value and final response, and test the hook lifecycle. Distinguish a failed final solve from response ordering and differing provisional timing.

3. Deadline termination cannot preserve an in-flight best result — high

corridorFinal.ts:211–229 treats budgetMs as metadata; evaluation count controls work. src/renderer/assets/final-planning.js:66–73 enforces the wall deadline by terminating the worker and returning interactiveResult. path-preview-worker.js:205–228 sends a result only after the solver returns. A slow solve can lose its validated best-so-far candidate. That loss is an inferred risk; no timeout was reproduced on the owner path.

4. Outcomes conceal why search was unhelpful — medium

corridorFinal.ts:265–285 discards deviation, solver, physical-validation, topology, gate, swept-footprint, and clearance rejection reasons. Unsupported inputs at lines 241–251 become equivalent, while line 347 says no material improvement. The UI's equivalent message cannot explain these distinct situations. The heuristic winner can also become optimal at line 353; local slowdown paths in optimizedTrajectory.ts:451–535 use that label without proving global optimality. Report validated improvement and scoped solver evidence.

5. Returned baseline validity is not established at every fallback boundary — high

src/shared/planners/fixedGeometryFinal.ts:222–230 returns the interactive baseline on candidate failure before the independent baseline check at line 233. Its fallback diagnostics set constraintViolations to zero at line 191. index.ts:191–202 can retain a baseline error. This is an acceptance-contract gap, not a reproduced invalid corpus trajectory. A fallback label cannot substitute for actual validation.

Architectural observations

src/shared/planners/index.ts:129–138 already routes normal and optimized families through shared physics-aware timing. Keep that strength. fixedGeometryFinal.ts:203–206 invokes both wrappers, while index.ts:242–270 may try a denser normal trajectory. Optional performance must be measured against the same validated normal baseline, rather than attributed to duplicate/regridded generation.

src/shared/export/bdx.ts:25–27 regenerates an optimized trajectory at export; App.jsx:371–414 separately plans routine paths. Current deterministic search reduces differences at matching settings, but there is no persisted accepted-candidate contract. If the product adds deeper effort, compare/apply, or per-path options, independent regeneration must not silently replace the selected result.

Current search preserves waypoint positions and handle directions and searches handle lengths inside a default 0.15 m corridor. It is not unrestricted route planning. Nonzero translational jerk is explicitly unsupported in optimizedTrajectory.ts:367–377, which also affects the normal family through sharing. Product controls and error messages must respect these actual capabilities.

Recommended disposition

Track the five findings as linked issues. The owner confirmed explicit per-path compare/apply, adjustable corridor freedom, a five-second target, and Optimize all. These decisions are recorded in the companion draft plan. Sequence the work as baseline correctness, result ownership, useful deterministic search with incumbent delivery, selected-result export consistency, then benchmark and robot evidence. Do not weaken constraints or normal-mode quality to improve optimizer success statistics.

Rebuilt LabVIEW Bordeaux writes a single path as raw, big-endian LabVIEW 4.4 flattened data; this checkout now emits that container, but its curve generation remains intentionally distinct and must not yet be called numerically identical.

Verdict: container-compatible, planner parity incomplete. The previous .bdx output was JSON and could not be read as a LabVIEW Bordeaux path. The new writer matches the proven v4.4 field layout, primitive encodings, units, and fixed 20 ms sample cadence, with an empty command list as requested. Exact clothoid, Bézier, and velocity-profile parity requires a dedicated compatibility planner and golden files generated by the rebuilt LabVIEW VIs.

Scope and evidence

The reference is frc2468/bordeaux, branch rebuilt, commit 2286086909363e117a408d140b6f707d920a17c5. The audit extracted front-panel typedefs, block-diagram resources, constants, and wires from the binary VI/CTL files and cross-checked the embedded papers and full Git history. The local implementation was reviewed at 1b8a127 plus the pre-existing uncommitted product work.

  • Binary contract: Versioned Write.vi, Versioned Load.vi, Path Stuff.ctl, Trajectory Data.ctl, and limits/waypoint typedefs.
  • Bézier math: Bezier Spline.vi, derivative/curvature VIs, 24-point quadrature VI, and the Lau and Bernstein–Fourier papers included in the reference.
  • Clothoid math: the complete generation chain from corner-angle calculation through normalized spiral integration, reflection, extra-arc handling, resampling, and overlap review.
  • Motion profiles: S-Curve2.vi, Newton/sigmoid helpers, clothoid acceleration helpers, and holonomic omega profiling.

Two old v3.1 path artifacts were recovered from commit 7feef6c. Their 00 00 00 03 33 2e 31 headers and numeric payloads corroborate the flattened-data conventions. They are useful historical evidence, not v4.4 golden fixtures.

The v4.4 binary contract

A .bdx file is not JSON, ZIP, an RSRC container, or a tagged message. It is a raw concatenation of flattened LabVIEW values. All numeric fields are big-endian/network order. Strings and one-dimensional arrays begin with a big-endian U32 byte/element count. Clusters are concatenated in typedef order with no alignment padding. Booleans are one byte. The first seven bytes of every v4.4 file are:

00 00 00 03 34 2e 34
└─ U32: 3 ─┘ └ "4.4" ┘
#Top-level valueFlattened contents
1VersionString 4.4
2DirectionRobot Backwards bool; Reverse Path bool
3Trajectory DataU32-counted trajectory-segment array
4Sorted commandsU32-counted command array; emitted as zero length
5Conditionssample period; linear limits; endpoint velocities; overrides; angular limits
6Updated WaypointsU32-counted {x,y,th} DBL clusters
7SummaryTime seconds DBL; Distance feet DBL
8Zero VelocityBoolean
9Path metadataDrive Type U16; Path Type U16
10–13Recent flagsPickup Balls bool; Current Limit DBL; Zero Translational Velocity bool; Correct at Beginning bool

Trajectory segment

String Segment Name
U16    Segment Type      // 0 Accel Straight, 1 Const Straight, 2 Blend,
                         // 3 Circle, 4 Bezier
Array   { DBL x, DBL y, DBL th }
Array   { DBL V, DBL Omega, { DBL vectorY, DBL vectorX } }
I32     Accel Index
I32     Decel Index

The velocity-vector order really is y then x in the LabVIEW typedef. Drive Type is 0 Nonholonomic or 1 Holonomic; Path Type is 0 Clothoid or 1 Bezier.

Conditions

DBL Sample Period (s)
{ DBL Velocity fps, DBL Accel fps², DBL Jerk fps³, DBL StoopidFast fps }
{ DBL vInitial fps, DBL vFinal fps }
Array { String Count, DBL Angular Override, Bool Enabled,
        DBL Velocity Override, DBL Angle Override }
{ DBL Angular Velocity deg/s, DBL Angular Accel deg/s²,
  DBL Angular Jerk deg/s³ }

The new writer emits one selected path, converts SI values at this boundary, samples at 0.02 s, writes no commands or overrides, and atomically replaces the destination. When the current planner duration is not an exact 20 ms multiple, it stretches the complete time mapping by less than one tick and scales velocity and omega with it, so the final waypoint and kinematics remain aligned to the declared fixed-time grid. Stored endpoint-velocity conditions come from the actual first and last emitted samples, including planner clamping and stops. This is intentionally a small schema-specific encoder rather than a generic LabVIEW serializer.

Bézier math

The reference uses degree-five Bézier segments, not the degree-three curve currently in pm.ts:

Q(u) = Σ[j=0..5] C(5,j) (1-u)^(5-j) u^j Pj

P0 = Wi                         P5 = Wi+1
P1 = Wi   + Ti/5                P4 = Wi+1 - Ti+1/5
P2 = Ai/20   + 2P1 - Wi         P3 = Ai+1/20 + 2P4 - Wi+1

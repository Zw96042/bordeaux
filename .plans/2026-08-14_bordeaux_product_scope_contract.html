Make Bordeaux the native FRC Java environment for authoring, optimizing, composing, and safely pushing autonomous routines to a robot.

Scope status: this contract records the owner's decisions from the August 14 grilling session. It authorizes planning and prioritization, not implementation by itself.

Product decision

Bordeaux serves the experienced Java controls programmer responsible for reliable autonomous routines. Its product wedge is the complete Bordeaux-native path-to-robot workflow: author geometry, optimize motion, compose paths with typed robot capabilities, inspect the result, and push validated routine data to a paired robot.

The planner is not merely an enabling component. It must become independently competitive with established FRC planners and optimizers, but Bordeaux's public identity remains the complete workflow rather than a solver benchmark.

Competitive planner contract

Bordeaux keeps two modes: an instant deterministic planner for editing and a deliberate final optimizer that may jointly change geometry and timing. A native solver dependency is acceptable behind the final optimizer when it is pinned, deterministic at the input boundary, license-compatible, packaged on supported platforms, and unable to break the interactive fallback.

Robot push contract

  1. Pair deliberately. Bind the target to the team number, accepted SSH host key, and Bordeaux runtime identity; require re-pairing after an identity change such as roboRIO reimaging.
  2. Trigger explicitly. A user chooses Push to Robot…; saving never pushes automatically. The preview names the robot, project, catalog, revision, and transport.
  3. Validate locally. Build bounded bordeaux-trajectory/1.0 data, validate the schema and command catalog, and calculate SHA-256 before transfer.
  4. Stage atomically. Upload a temporary sibling under /home/lvuser/deploy/bordeaux, verify bytes and hash, then use a same-directory atomic rename into a stable slot.
  5. Activate safely. Robot-side systems must respond, report disabled, match the compiled catalog, load the revision, and acknowledge its SHA-256. Bordeaux distinguishes uploaded, staged, rejected, and active states.
  6. Recover deliberately. Keep the five latest accepted revisions plus one user-pinned known-good revision; rollback activation is disabled-only and acknowledged like a normal push.

Wi-Fi, Ethernet, and USB are equivalent when SFTP is reachable. Port 22 is unavailable on the FMS field network, so Bordeaux reports pushing as unavailable there rather than adding a second field-transfer protocol.

Routine and extension contract

The external beta ships an export-safe routine surface: typed commands, sequences, decisions, and simple built-ins. Team capabilities are registered in compiled Java, discovered through an authoritative catalog, and referenced from project data by stable ID and typed arguments.

Custom runtime trajectory generation is a post-beta goal. A generator must declare typed inputs, output and kinematic bounds, spatial constraints, a timeout, and fallback behavior. The runtime validates every generated segment. If generation times out or returns an invalid segment, the routine branch aborts into a safe stop unless the author explicitly attached a validated fallback branch. When exact desktop preview is impossible, Bordeaux labels the segment dynamic instead of pretending to know its path.

Seasonal contract

  • Ship the official field image and coordinate model within 48 hours of kickoff.
  • Ship fully verified obstacles, portals, vocabulary, clearances, and agent-planning behavior within seven days.
  • Deliver seasonal support through a normal signed GitHub application release using the existing updater; independent field-pack infrastructure is deferred.
  • Persist the field ID and schema version in each project. Opening an older project never silently reinterprets coordinates, geometry, or obstacles.
  • Before claiming full support, cross-check official drawings, CAD, and the game manual; run coordinate, symmetry, obstacle, portal, clearance, and representative-route simulation tests.

Local readiness model

This local-only control checks the agreed entry gates and exports their state. The hosted plan remains a static contract because The Lab disables arbitrary scripts.

External beta blocked: six non-benchmark gates remain.

Beta outcome

After entry, success means at least five outside teams author, push, and run a real autonomous routine; at least three return for another use; and no critical incorrect-output incident occurs. Evidence comes from explicit diagnostic bundles and structured cohort check-ins, not passive telemetry.

Explicit non-goals

  • PathPlanner or Choreo import, migration, export, or bidirectional compatibility. Full Bordeaux behavior requires a Bordeaux-native project.
  • Python, C++, or LabVIEW integration on the maintained application branch.
  • Cloud projects, accounts, synchronization, collaboration, or passive analytics.
  • Arbitrary desktop plugins, uploaded executable scripts, robot-code compilation, or GradleRIO deployment.
  • A second transfer service for FMS-field pushing.
  • FTC, general robotics, or non-FRC field support.
  • Field-agnostic pack infrastructure before annual app-release delivery proves insufficient.

Execution sequence

  1. Make product truth explicit. Hide simulation-only routine templates, add Apache-2.0, reconcile current scope records, and keep competitive claims out of product copy until evidence exists.
  2. Build the neutral benchmark. Freeze the two-class corpus, adapters, dense validator, raw result format, and reproducible runner before tuning a final solver.
  3. Build the final optimizer. Preserve interactive planning, introduce cancellable bounded final optimization, and earn the majority-win gate without invalid outputs.
  4. Close the robot loop. Add explicit pairing, push preview, atomic staging, disabled-only activation, runtime acknowledgment, revision history, and rollback.
  5. Polish the native workflow. Ensure commands, sequences, decisions, simple built-ins, Java discovery, export, and robot execution form one coherent path without migration features.
  6. Certify and recruit. Pass seasonal, signing, update, safety, and real-robot gates; then recruit the five-team cohort and evaluate the outcome contract.

Verification

  • Each implementation plan must trace its acceptance criteria to one contract section and identify any non-goal it could accidentally expand.
  • Planner claims require committed raw results from the frozen corpus; passing unit tests alone is insufficient.
  • Robot delivery requires a real-device test covering wrong identity, stale catalog, enabled robot, interrupted upload, invalid hash, successful activation, and rollback.
  • Release validation includes repository tests, type checks, builds, Electron smoke tests, signed-package verification, updater verification, and the applicable seasonal certification suite.
  • At beta entry, export the readiness model as JSON and attach concrete evidence for every true gate.

Open questions

None. Changes to the product boundary, benchmark gates, robot activation contract, annual field promise, or explicit non-goals require an intentional revision of this plan.

File and data design

The direct BDXLV1 contract is now explicit: a 32-byte version/length/CRC header, metadata, 11-DBL samples, follow sections and typed command events. The app writer emits these fixed big-endian sections; the matching reader uses LabVIEW primitives and ordinary VIs. The earlier CBOR plus native-decoder proposal is superseded; it must not dictate a generic serialization framework or a new runtime dependency.

The file must retain the selected path ID/name, timed samples, position and robot/travel heading, follow modes and command schedules. Command values must preserve exact NI integer widths, strings, Boolean/numeric values, and enums. Unsupported compound parameters are rejected explicitly. Preserve defaults and wrapper behavior from actual NI evidence. Unrelated paths and routines do not enter the export.

Writing is local and never connects to a robot. File values do not choose arbitrary executable VIs or silently establish command readiness. Use the project's actual included command wrappers and verified parameter mapping. No AQU writer, reader, storage fixtures or executor is included.

Implementation pass

  1. Save context and revise the contract. XPS archives the superseded native plan, keeps the current study clear, and supplies the direct-VI byte layout and .ctl definitions to the app implementer.
  2. Adapt the app writer. Preserve the selected-path compiler, full command data and local export workflow; replace any format assumptions that require the native library. Generate exact test files with expected NI values.
  3. Author the reader in robot code. Use MCP to create and wire normal reader/validation VIs and typedefs in the isolated Apprentice project. Validate lengths, versions, types and failure behavior before populating path data.
  4. Implement the single-path runner. Follow the existing Play Path/Drive Controller pattern with direct VI timing, measured progress, sample handling, command dispatch and completion. Reuse audited team drive helpers.
  5. Implement stop and cancellation. Inhibit further dispatch, cancel all autonomy-dispatched commands, resolve notifiers, zero drive and release resources on stop/disable/error. Stale work must not reactivate a finished path.
  6. Verify real integration. Read app-generated BDX files in NI; save/reopen with a clean Error List; run a hardware-free harness for paths, typed commands and stop behavior; independently inspect changed source and diagrams. Then finish relevant app build/UI checks.

Verification and preservation

  • Golden BDX files cover plain and curved paths, heading versus travel direction, empty and populated command schedules, exact parameters, repeat/end policies and representative malformed files.
  • Reader failures must leave no partially ready path or running command. Test wrong format/version, truncation, excessive lengths, invalid numeric/types, unsupported commands and corrupt data.
  • Desktop NI harness supplies clock/pose/mode, mock command/notifier adapters and captured drive outputs; inspect its dependency closure before Run.
  • Preserve the original open/unsaved projects. Work in the isolated full copy backed by the verified 1,356-file disk backup; disk backup does not capture unsaved edits.
  • No physical robot connection, target build/deployment, enabling or actuator movement is authorized by this pass. Host-code or prototype tests are not NI or robot verification.

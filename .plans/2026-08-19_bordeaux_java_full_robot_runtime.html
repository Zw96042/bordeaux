Bordeaux Java Full Robot Runtime

Projectbordeaux
Versionv4
Statusactive · 2026-08-19

Turn the Java support package into a complete robot-side runtime: existing commands in, authored or generated paths through localization and control, safe drivetrain output out.

Scope change. The earlier product-scope contract stopped Bordeaux before drivetrain control. This plan intentionally supersedes that boundary for the Java runtime. Bordeaux will own path/routine execution, control, optional pose estimation, vision fusion, tuning, diagnostics, and safe stop. Teams still own wiring, motor-controller configuration, mechanical limits, deployment, and final hardware safety.

Outcome contract

A team with an existing command-based robot should be able to expose its drivetrain through method references, keep every current teleop and autonomous command, and obtain a fresh ordinary WPILib Command for a Bordeaux path, routine, or bounded runtime-generated path. The same command must work in choosers, triggers, command groups, and @BordeauxCommand methods.

“Full functionality” means the runtime owns the complete chain below, not just file parsing or command lookup.

  • Static and runtime-generated trajectory execution with path events, routine decisions, waits, fallbacks, and result reporting.
  • Tunable holonomic following with velocity, acceleration, angular-rate, and curvature references preserved end to end.
  • Two localization modes: wrap the team's existing estimator, or let Bordeaux own a WPILib swerve estimator.
  • Timestamped multi-camera pose correction with covariance, latency handling, outlier rejection, and health diagnostics.
  • Disabled-only atomic tuning by default, plus explicit bounded live-tuning and SysId/characterization hooks.
  • Safe preflight, subsystem requirements, stale-state detection, bounded generated paths, deterministic stop, and simulation.

Recommended interface

BordeauxRuntime is the deep module. Callers learn one builder and ask it for commands; the existing reader, follower, routine, event, generation, and revision classes become its internal machinery while remaining available during migration.

var drive = BordeauxDriveAdapter.forSubsystem(drivetrain)
    .state(() -> new BordeauxDriveState(
        drivetrain.getPose(),
        drivetrain.getRobotRelativeSpeeds(),
        drivetrain.getStateTimestampS()))
    .output(drivetrain::driveRobotRelative)
    .resetPose(drivetrain::resetPose)
    .visionMeasurement(drivetrain::addVisionMeasurement)
    .stop(drivetrain::stop)
    .limits(new BordeauxDriveLimits(4.8, 7.0, 9.0, 18.0))
    .build();

bordeaux = BordeauxRuntime.builder(drive, BordeauxBindings.generatedCapabilities(this))
    .vision(BordeauxVisionSource.of("front", vision::drainObservations))
    .build();

Command auto = bordeaux.auto("four-piece");
Command driveTo = bordeaux.generateAndFollow("drive-to-pose", targetPose);

The default seam is deliberately above motor and module vendors: corrected Pose2d and measured robot-relative ChassisSpeeds come in; validated robot-relative ChassisSpeeds go out. A second, advanced adapter lets Bordeaux own module kinematics, IMU sampling, pose estimation, feedforward, and characterization.

Compatibility claim. Bordeaux can be broadly compatible without pretending all hardware is identical. The generic adapter is the universal path. Named vendor adapters are conveniences, independently versioned and tested against a published compatibility matrix.

Execution and safety invariants

  1. Validate the active artifact, field identity, drive limits, command arguments, start pose, generator limits, and every reachable routine branch before enabling motion.
  2. Read one atomic timestamped robot state; apply timestamp-ordered vision corrections; freeze it for the control iteration.
  3. Advance the path/routine/generator state, calculate control output, validate finite values and limits, then issue exactly one drive request.
  4. Require the drivetrain subsystem for every motion command. Reject path events that would unexpectedly steal that requirement.
  5. On interruption, stale state, invalid controller output, adapter failure, or failed generation containment: stop once, retain a stable fault/result, and never throw through robotPeriodic.
  6. Use the WPILib blue-origin field frame and FPGA timestamps at public seams. Apply alliance transforms exactly once. Never silently zero vendor IMU hardware.
  7. Stage tuning only while disabled by default. Snapshot gains at run start so an autonomous run cannot change beneath itself.

Delivery map

  1. #147 Complete trajectory and adapter contracts. Preserve acceleration, angular velocity, curvature, and travel direction separately from robot heading; add normalized drive, localization, vision, result, limits, and fault types without breaking existing callers.
  2. #148 Tunable holonomic follower. Convert full trajectory states plus current pose into bounded robot-relative ChassisSpeeds, with start-pose policies and an ordinary command lifecycle.
  3. #149 Localization and vision. Support a team-owned estimator first, then a Bordeaux-owned SwerveDrivePoseEstimator path with delayed multi-camera corrections and diagnostics.
  4. #150 One runtime facade. Compose the existing routine, event, generation, fallback, capability, and revision machinery behind BordeauxRuntime.
  5. #151 Tuning and characterization. Add typed bounded parameters, atomic disabled-only NetworkTables transactions, telemetry, SysId command factories, and reproducible reports.
  6. #152 Adapter packs and examples. Certify CTRE Phoenix 6, YAGSL, custom WPILib swerve, PhotonVision, Limelight, common IMUs, and import bridges through optional artifacts.
  7. #153 Simulation and compatibility certification. Run deterministic fake-drive/fake-vision tests, WPILib simulation, vendor compile matrices, stale/fault tests, and full generated-path containment tests.

Verification gates

  • API tests prove fresh commands, WPILib requirements, safe interruption, retained results, and reuse of existing command bindings.
  • Golden trajectory tests prove every exported motion field reaches the follower and legacy trajectory documents still load deterministically.
  • Controller tests cover straight, curved, rotating, reversed, stationary-action, start-pose mismatch, saturation, and stale-state cases.
  • Fusion tests use delayed, reordered, duplicate, future, high-innovation, and multi-camera measurements with deterministic timestamps.
  • Generation tests prove timeout, sample, dynamics, field, collision, fallback, cancellation, and result handoff through the same command.
  • Adapter compile/simulation matrices cover supported WPILib and vendor versions; hardware support is published only after a repeatable smoke test.
  • Repository gates remain focused on Java modules; GUI and website files are outside this implementation program.

Primary references

  • WPILib holonomic controller — the standard pose/reference-to-chassis-speed control seam.
  • WPILib pose estimators — delayed vision correction over drivetrain odometry.
  • WPILib SysId routine — command-based characterization hooks.
  • WPILib gyro APIs and coordinate conventions — normalization requirements for IMU adapters.
  • PhotonVision pose estimation — capture timestamps and estimator measurement delivery.
  • CTRE Phoenix 6 swerve and YAGSL vision odometry — examples of existing estimators that should sit behind the default adapter.

Non-goals

  • Automatically discover hardware, rewrite vendor configuration, or claim support without a versioned test matrix.
  • Replace WPILib's scheduler, geometry, kinematics, or standard robot lifecycle.
  • Move safety-critical vendor code into core or require direct module access from teams that already have a working drivetrain.
  • Modify the Bordeaux GUI or website as part of this Java runtime work.

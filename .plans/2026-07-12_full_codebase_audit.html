Bordeaux Full Codebase Audit

Projectbordeaux
Versionv1
Statusactive · 2026-07-12

The product has a strong visual foundation and useful trajectory math, but it is not ready to trust with project persistence or robot deployment: the shipped UI cannot save projects, autonomous routines are omitted from export, and malformed geometry can serialize invalid motion data.

Verdict: request changes before release. One critical workflow defect can lose all user work. Several high-impact correctness, deployment-contract, security, and accessibility issues affect exported robot behavior and core use. The recommended sequence is data integrity first, renderer consolidation second, then accessibility and production hardening.

Scope and method

Read-only audit of the current checkout at commit 1b8a127 on main, including the two pre-existing working-tree changes in package.json and scripts/extract-standalone.mjs. Inspected all TypeScript source, the generated legacy renderer, Electron IPC, trajectory planners, validation/export paths, package/build configuration, tests, and live runtime behavior at 1440×920.

  • Static inspection: roughly 3,100 typed source/test lines plus the generated renderer and extraction pipeline.
  • Runtime inspection: Electron launch, DOM/accessibility tree, computed UI structure, and targeted data-corruption/trajectory probes.
  • Verification: tests, both TypeScript builds, build script, dependency audit, and working-tree/diff checks.

Detailed findings

1. Project persistence is absent from the shipped UI — Critical

Evidence. src/electron/main.ts:38 loads public/legacy/index.html. Menu actions send menu-command at main.ts:67–74, but only the unused typed renderer subscribes at src/renderer/App.tsx:78–82, 169–187. The legacy renderer only calls direct export at public/legacy/assets/34f…js:349–361. It contains no dirty state, beforeunload, open, or save integration.

User impact. Users can spend a full session authoring paths and lose everything on close. Native menu commands appear valid and fail silently, which is worse than a visibly unavailable feature.

Smallest fix. Pick the canonical renderer, wire New/Open/Save/Save As and dirty-close protection end to end, report success/failure in the UI, then add one Electron smoke test that performs the complete lifecycle.

2. Auto “Deploy” has no contract for the routine being authored — High

Evidence. The shipped app initializes independent routine state at 34f…js:68 and edits/runs it at 303–335. The Auto toolbar labels the same path-export action “Deploy” (public/legacy/assets/796c…js:113–118), but BdxExport has no routine field (src/shared/types.ts:225–242) and buildBdxExport returns only robot and paths (src/shared/export/bdx.ts:45–62). Routine path nodes also use numeric indices (src/shared/types.ts:97–101) that delete/duplicate operations do not repair (34f…js:283–286).

User impact. The UI promises deployment from the routine workspace while producing a path-only artifact. Whether this is release-blocking depends on the intended downstream contract, but the current label and behavior are materially misleading. Structural path edits can also retarget routine steps.

Smallest fix. Decide and test the contract: version/extend .bdx to include routines, emit a separate routine artifact, or relabel/remove “Deploy” if the feature is simulation-only. Independently, persist routine state in the project and replace index references with stable path IDs.

3. Nested numeric corruption passes validation — High

Evidence. src/shared/validation.ts:33–39 checks waypoint positions and only the presence of handles, not handle coordinates. It also omits headings, targets, markers, ranges, endpoint velocities, angular limits, schema version, and planner ID. A focused probe with a string handle coordinate returned validationOk true, generated 57 samples containing non-finite numbers, and produced 170 JSON null values.

Smallest fix. Fully validate the serialized boundary, with Number.isFinite for every numeric field and bounds/enums where applicable. After planning, reject any non-finite sample or summary field before writing.

4. Export bypasses its own blocking diagnostics — High

Evidence. previewBdxExport incorporates path diagnostics and sets ok:false for high-severity issues (src/shared/export/bdx.ts:65–91). IPC export calls buildBdxExport directly (src/electron/main.ts:138–150), which returns diagnostic errors but does not block them. A verified tight-turn probe produced radius ≈0.12 m: preview rejected it while build returned export data.

Smallest fix. Centralize one export policy used by preview and write. Block errors by default; if overrides are a product requirement, require explicit informed confirmation and preserve the diagnostic in the file.

5. Optimized event-marker timing is mathematically wrong — High

Evidence. Samples are retimed segment by segment in src/shared/planners/optimizedTrajectory.ts:13–43, then all marker times are multiplied by one total-duration ratio at 138–146. A localized-stop probe measured an exported marker time of 2.0414 s versus 2.1724 s interpolated from final samples: a 0.1310 s error.

Smallest fix. Interpolate each marker fraction against the final sample f/t curve. Add tests with slowdowns and stops on both sides of multiple markers.

6. Two renderers create a false verification boundary — High

Evidence. Electron loads generated legacy assets, while src/renderer/main.tsx is the source TypeScript checks. npm run build only runs the Electron TypeScript compiler. The legacy app is regenerated through a large exact-string patch script, and shipped React/ReactDOM are development builds.

Impact. UI fixes, types, and tests can all be correct for code users never run. Generated files are expensive to review and easy to drift.

Smallest fix. Prefer migrating the current UX into the typed renderer. Acceptance criteria: one renderer entrypoint; one production build artifact; Electron loads that exact artifact; shipped assets contain no development React; and one smoke test exercises launch plus persistence/export. If legacy must remain temporarily, declare it canonical, lint/test it directly, and assert its generation stamp during build.

7. Electron privileges exceed renderer trust — High

Evidence. The preload accepts arbitrary open/save/export/reveal paths (src/electron/preload.ts:4–10); main consumes them without sender/origin checks (main.ts:120–155). Chromium sandboxing is disabled at main.ts:32. The loaded document has no CSP or navigation/window-open denial. npm audit --omit=dev reports Electron 37.10.3 as a high-severity vulnerable production package. The shipped UI does not currently pass arbitrary output paths, so arbitrary file overwrite requires a compromised renderer; this is a privileged-boundary risk, not a demonstrated exploit.

Smallest fix. Upgrade to a patched Electron release, enable sandboxing, add a restrictive CSP and navigation policies, validate IPC sender/frame, and keep current file paths in main. Expose intent-based calls such as saveCurrent rather than general path-bearing filesystem calls.

8. Unknown JSON can crash validation; save is not a safe boundary — Medium

Evidence. validateProject reports a non-array paths field, then still calls forEach at src/shared/validation.ts:18,27. Null path entries and string waypoint containers also throw. Save does not validate and truncates the destination directly at src/electron/main.ts:122–135.

Smallest fix. Treat these as two acceptance tracks: (a) guarantee validateProject(unknown) never throws, reject unsupported schema/planner values, and reuse it at open/save/export; (b) serialize saves per target and write a sibling temporary file followed by atomic rename.

9. Accessibility semantics block keyboard and assistive-tech users — Major / High

WCAG. 1.3.1 Info and Relationships, 2.1.1 Keyboard, 4.1.2 Name/Role/Value.

Evidence. Live Chromium accessibility inspection found 50 exposed controls, 11 without accessible names, seven clickable div elements outside native keyboard behavior, zero main/nav landmarks, and no aria-label attributes on 35 buttons. Field geometry is an SVG/pointer workflow without an equivalent structured editor path for all operations. Outline disclosures use button roles without normal tab/Enter/Space behavior, numeric controls are visually but not programmatically labeled, and many controls define hover styles while inputs/ranges suppress the native outline without a strong :focus-visible replacement.

Smallest fix. Use native buttons for clickable rows, programmatically label all fields/icon controls/sliders, expose selected/expanded states, add landmarks and logical headings, ensure every canvas action has a keyboard route, and add one global high-contrast focus-visible treatment. Then test with keyboard plus VoiceOver/NVDA. Automated checks are a floor, not the completion criterion.

10. Low-contrast tokens weaken readability — Major / Medium

WCAG. 1.4.3 Contrast (Minimum).

Evidence. --txt-3: #5f656e is used for 9.5–12px labels on #0b0c0e/#16181b, measuring roughly 3.1–3.35:1. The default blue active text measures about 3.7–3.95:1 on common dark surfaces. Normal text requires 4.5:1.

Smallest fix. Raise muted and active text tokens, separate decorative from textual accent usage, and run contrast checks across slate, forest, amber, cyan, and violet themes.

11. Destructive flows lack recovery — Medium

Evidence. Path deletion at 34f…js:285 is immediate, has no confirmation, and sits outside the per-path undo stack. Routine-step deletion is likewise direct.

Smallest fix. Make deletion undoable at project scope or confirm high-value path/branch removals, and verify selection/reference state after undo.

12. Green checks do not cover the product boundary — Medium

Evidence. All 13 tests are in tests/bdx.test.ts. The only shipped-renderer check asserts string fragments in a generated bundle. There are no IPC, startup, open/save/export failure, routine deployment, unsaved-close, packaged-app, accessibility, or malformed-file tests; no CI config or lint command exists.

Smallest fix. First add regression tests for findings 2–5 and malformed validation. Then add one Electron smoke suite for launch → edit → save → reopen → export → close, and run test/typecheck/build/audit in minimal CI.

Additional engineering observations

  • False diagnostics: constraintViolations is hard-coded to zero in optimizedTrajectory.ts:98–109. Calculate it from final samples or remove the claim.
  • Main-process stalls: file reading is asynchronous, but JSON parsing and trajectory generation run synchronously in main IPC with no file/count limits. Cap inputs and move expensive planning off main when projects become large.
  • Type escape hatch: the 543-line core math engine is // @ts-nocheck, and consumers use any. A typed adapter around its return value is a smaller first step than rewriting it.
  • Production weight: the legacy renderer embeds development React/ReactDOM; ReactDOM alone is about 1 MB/29,924 lines.
  • Export feedback: the shipped handler does not await export, disable duplicate clicks, report cancellation, or show success; failure falls back to blocking alert(). Add pending state, a calm error, and a success toast with filename/reveal action.
  • Zoom/reflow: the window enforces 1100×720, uses fixed side rails, and hides root overflow. At 200% zoom the non-field chrome can clip. Collapse rails/tool labels and provide overflow before sacrificing the editor.
  • Popover semantics: path/theme/context menus lack complete expanded-state, Escape, focus management, and arrow-key behavior. Prefer normal-button popovers unless full menu semantics are implemented.
  • Naming and recents: duplicate path names are allowed, while the recent-files list only lives for the current process. Disambiguate or validate names and persist a bounded recent list after the persistence flow exists.
  • Tooling drift: Vite and several helper dependencies are installed but unused by current scripts; there is no packaging command or contributor README.

What is working well

  • The live UI has a clear, calm visual hierarchy suited to an engineering tool: strong field focus, persistent outline/inspector, coherent constraint vocabulary, and useful inline diagnostics.
  • contextIsolation:true and nodeIntegration:false are good baseline Electron choices.
  • Shared planner/export boundaries are compact, planner selection is explicit, and existing tests cover default export, stops, markers, path exclusion, optimized output, and clothoid continuity.
  • Strict TypeScript is enabled outside the legacy/math escape hatches, and the current test/type/build checks are fast enough to run on every change.

Recommended remediation sequence

  1. Stop data loss: connect persistence, dirty-close protection, routine/project state, stable path references, and safe project-wide undo.
  2. Make export trustworthy: total schema validation, finite-output checks, shared diagnostic blocking, correct marker retiming, and honest constraint diagnostics.
  3. Unify the product boundary: select one renderer, make build load exactly what it validates, and add Electron lifecycle tests.
  4. Harden the desktop shell: Electron upgrade, sandbox/CSP/navigation rules, intent-based IPC, atomic saves, and input limits.
  5. Make the UI inclusive: semantic controls, accessible names/states, keyboard parity, contrast fixes, reduced-motion review, and assistive-tech testing.
  6. Productionize: CI, linting, packaging/signing/update documentation, production React bundle, and cleanup of unused dependencies.

Reproduction appendix

Install the lockfile and compile the shared modules first:

npm ci
npm run build

The following probe reproduces the malformed-handle, diagnostic-policy, and optimized-marker findings against the compiled shared code:

node - <<'NODE'
const { createDemoProject, buildWaypoints } = require('./dist-electron/shared/project/defaults.js');
const { validateProject } = require('./dist-electron/shared/validation.js');
const { buildBdxExport, previewBdxExport } = require('./dist-electron/shared/export/bdx.js');

const bad = createDemoProject();
bad.paths[0].waypoints[0].nextC.x = 'not-a-number';
const badOut = buildBdxExport(bad);
const badSamples = badOut.paths[0].samples.filter((sample) =>
  Object.values(sample).some((value) => typeof value === 'number' && !Number.isFinite(value)),
);
console.log('malformed', {
  validationOk: validateProject(bad).ok,
  badSamples: badSamples.length,
  jsonNulls: (JSON.stringify(badOut).match(/null/g) || []).length,
});

const tight = createDemoProject();
tight.paths[0].waypoints = buildWaypoints([
  { x: 1, y: 1, theta: 0, segType: 'bezier' },
  { x: 1.05, y: 7, theta: 0, segType: 'bezier' },
  { x: 1.1, y: 1, theta: 0 },
]);
console.log('tight', {
  previewOk: previewBdxExport(tight).ok,
  buildDiagnostics: buildBdxExport(tight).paths[0].diagnostics,

const markerProject = createDemoProject();
markerProject.plannerId = 'optimizedTrajectory';
markerProject.paths[0].waypoints = buildWaypoints([
  { x: 2.2, y: 4, theta: 0, segType: 'bezier' },
  { x: 3.2, y: 4.7, stop: true, segType: 'bezier' },
  { x: 5.4, y: 4, theta: 0 },
]);
markerProject.paths[0].markers = [{ f: 0.66, name: 'm' }];
const retimed = buildBdxExport(markerProject).paths[0];
const i = retimed.samples.findIndex((sample) => sample.f >= 0.66);
const a = retimed.samples[i - 1], b = retimed.samples[i];
const expected = a.t + ((0.66 - a.f) / (b.f - a.f)) * (b.t - a.t);
console.log('marker', {
  exported: retimed.markers[0].timeS,
  interpolated: +expected.toFixed(4),
  delta: +Math.abs(retimed.markers[0].timeS - expected).toFixed(4),
});

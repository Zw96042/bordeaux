Agent Path Authoring Through an MCP Server

Projectbordeaux
Versionv2
Statusactive · 2026-08-05

Give agents a safe, typed way to understand the current Bordeaux project, translate 2026 REBUILT field language into geometry, generate and compare legal trajectory candidates, and stage the best candidate for review inside the app.

Outcome

A user should be able to tell an MCP-capable agent: “Start under our scoring-table-side TRENCH, go to the far edge of the NEUTRAL ZONE, come back to our shooting pose, and shoot using the fastest safe route.” The agent reads Bordeaux's field and robot context, resolves the named places, requests route candidates, and stages a proposal. It must also be able to inspect a pre-made or imported path, read its raw authored and sampled values, explain measured problems, and stage a focused repair. Bordeaux overlays every proposed change and its diagnostics on the field. The project changes only when the user clicks Apply in Bordeaux.

Optimization claim. “Best” means the fastest valid trajectory among the candidates Bordeaux generated under the selected robot, field, clearance, traversal, and action constraints. It is not a proof of a globally optimal autonomous routine. The UI and tool result must say which objective and candidate set were evaluated.

Recommended architecture

Ship one Bordeaux integration with two process roles:

  • Running desktop app: owns the live session, field data, route engine, planner calls, proposal store, and user approval UI.
  • Packaged --mcp-stdio mode: the MCP client launches the Bordeaux executable as a small stdio adapter. It authenticates to the running app over user-private OS IPC and translates MCP tools/resources into app-session requests.

This is preferable to an unauthenticated localhost port. Stdio is the normal local MCP integration model, while the private socket/named pipe keeps other websites and network peers away from the app. A direct Streamable HTTP endpoint can be reconsidered later if a target client cannot spawn a local process.

Connection and security contract

  • Add Agents → Enable MCP Access, disabled by default, with connection status and Copy MCP configuration. The copied command points to the installed Bordeaux executable with --mcp-stdio; it contains no secret.
  • The app creates a per-launch socket or named pipe plus a random nonce. The runtime descriptor lives under Electron userData with owner-only permissions. The adapter validates PID/start nonce and authenticates every connection.
  • No TCP listener in v1. The adapter returns a clear “Open Bordeaux and enable MCP access” error when the session is unavailable.
  • Bound every string, array, project snapshot, candidate count, sample count, request duration, and proposal lifetime. Cancel planner work when the MCP request is canceled or the app closes.
  • Annotate MCP tools accurately, but enforce read-only versus proposal versus commit behavior in code; annotations are not the security boundary.

This follows MCP guidance to prefer stdio for local servers or otherwise protect local endpoints with authorization/restricted IPC. See the MCP security best practices and the official TypeScript server guide.

The renderer increments revision for every project or planner mutation. A proposal becomes stale as soon as its base revision no longer matches; it may be regenerated, never force-applied. Applying uses the renderer's existing commit/history path, selects the new path, marks the project dirty, and preserves stable path IDs and naming rules.

2026 field vocabulary model

Create src/shared/field/fieldPack.ts plus a built-in 2026-rebuilt fixture. A field pack is data, not prompt text:

  • Geometry: field boundary; HUB, BUMP, TRENCH, TOWER, DEPOT, guardrail, and keep-out polygons; NEUTRAL ZONE, ALLIANCE ZONE, CENTER LINE, ROBOT STARTING LINE, and named boundary segments.
  • Traversal: “under trench” portals with opening dimensions and approach corridors; “over bump” surfaces with traversal penalties and optional local speed caps; non-traversable structure solids inflated by robot footprint.
  • Language: official names, common lowercase aliases, alliance-relative qualifiers (our/opponent), side qualifiers (scoring-table/non-scoring-table), near/far resolution relative to a known start pose, and robot-relative directions (front/back/left/right).
  • Provenance: season, field revision, coordinate-frame statement, source document URLs, update date, and a fixture checksum.

Use one canonical blue-origin coordinate frame. Red requests are transformed into that frame before creating PathDoc geometry, matching the renderer's existing 180-degree alliance view. Official manual terms define semantics; exact dimensions are transcribed once from official field drawings and tested against the renderer calibration.

Ambiguity is data. “Under the trench” is ambiguous when both side TRENCHES are viable. “Far side of the neutral zone” requires an alliance or start pose. The resolver returns ranked alternatives with reasons; it does not silently choose left/right or our/their.

Robot-relative language uses the physical chassis frame at a named pose or trajectory sample: front is positive chassis X, back is negative chassis X, and left/right are perpendicular to the physical heading. Direction of travel is a different concept. When driveBackward is active, resolve the authored heading first and then apply the existing 180-degree physical-heading transform before interpreting front/back. If no pose/sample is specified and more than one is plausible, return ambiguity rather than using the active viewport or path tangent implicitly.

Team strategy vocabulary

The manual cannot define a team's best shooting pose or robot command. Add a small project-owned strategy overlay with named poses/regions and action bindings. Examples: our-safe-shot, centerline-intake-lane, and capability shoot-fuel. This metadata is editor-only, optional, additive to project schema 1.0, and preserved in project save/round trips but not reconstructed from imported .bdx.

Extend @BordeauxCommand and the generated catalog with optional bounded semantic tags/aliases. “Shoot” resolves only when exactly one linked runtime-ready command advertises the matching capability, or when the project overlay explicitly selects one. Otherwise the proposal ends at the shooting pose with an unresolved-action warning and no invented event marker.

Route generation and optimization

  1. Resolve the structured request. Convert every named start, destination, corridor, action pose, heading, and alliance qualifier to canonical geometry. Stop when required terms remain ambiguous.
  2. Build configuration space. Inflate solid field elements by the robot's actual half-width/half-length plus the selected clearance. Treat TRENCH portals and BUMPS as typed traversals, not empty space.
  3. Generate bounded route skeletons. Use a visibility graph or small navmesh over portals, obstacle corners, named lanes, and goal regions. Respect required phrases such as “through the TRENCH”; do not search an unconstrained continuous field.
  4. Fit authored geometry. Convert each skeleton to a minimal PathDoc using existing waypoint builders and planner-appropriate segment types. Reject self-intersections, field exits, obstacle intersections, invalid look-at singularities, and infeasible traversal approaches.
  5. Time with the real planner. Run the selected shared planner on each clone, apply range constraints and stationary actions, and collect total time, distance, minimum clearance, peak curvature, peak angular rate, fallback status, and diagnostics.
  6. Rank honestly. Invalid candidates never rank. By default minimize total trajectory time; if candidates are within the near-tie window, prefer more clearance, then less curvature/rotation demand, then fewer waypoints. Return the top three and the exact reason one won.
  7. Stage, do not commit. Send candidates to the renderer as dashed overlays with traversal labels, ETA, distance, clearance, diagnostics, and an Apply/Reject control. Applying is one history entry.

Existing-path analysis and repair

  1. Analyze without mutation. Normalize and validate the selected path, generate it through the shared planner, and expose bounded raw sample arrays plus summarized extrema. Every reported finding includes severity, measured value, authored limit, sample index/time/distance/fraction, segment, and nearest authored waypoint/range.
  2. Explain provenance. Distinguish authored values, normalized defaults, planner output, measured violations, and neutral planner slowdowns. Preserve planner fallback reasons and never call an expected curvature- or rotation-limited slowdown an error.
  3. Repair one target at a time. A repair request names one or more analysis finding IDs. Generate candidate handle, waypoint, segment, heading-law, range, or constraint changes only when they directly address those findings.
  4. Prove the candidate is better. Re-run complete validation and path checks on a clone. A candidate must remove or materially reduce the target finding, introduce no worse finding, preserve unrelated metadata/actions, and show an authored-field diff plus before/after metrics.
  5. Preview before Apply. Stage original and repaired geometry together, including changed raw values and the exact findings resolved. Imported .bdx projects retain their Save As behavior.

Acceptance scenario

  1. Bordeaux is open on a blue-alliance project with a linked robot catalog and a team strategy overlay defining safe-shot and a shoot-fuel command.
  2. The user asks an agent: “Start under our scoring-table-side trench, go to the far side of the neutral zone through the trench, come back to the safe shot, and shoot in the fastest safe way.”
  3. The agent reads the session and field resources. All field terms resolve unambiguously; the action resolves to one authoritative command.
  4. plan_path returns up to three candidates with exact ETA, distance, minimum clearance, traversal, diagnostics, and recommendation reason. No project data changes yet.
  5. Bordeaux shows the recommended dashed overlay and alternatives. The user can switch candidates and inspect the event location and arguments.
  6. The user clicks Apply. Bordeaux creates/selects one uniquely named path, adds the typed shoot marker, records one undo step, marks the project dirty, and updates the MCP proposal status to applied.
  7. Undo restores the prior project. Save/export continue through the existing app controls.

A second acceptance flow starts from a pre-made path: “Analyze this path's raw values and fix the acceleration spike near the back of the bot after it clears the TRENCH.” Bordeaux resolves “back” from the physical sample heading, reports the measured spike and its authored source, stages only candidates that improve that finding without worse checks, and waits for Apply.

Verification

  • Session unit/integration: revision increments, request timeouts, renderer reload, no active project, malformed response, stale proposal, Apply/Reject/Expire, undo, dirty state, unique path naming, active-path selection.
  • Field fixtures: coordinate transforms are involutive; red/blue landmarks mirror correctly; official named geometry aligns with calibrated renderer fixtures; TRENCH portals and obstacle polygons stay inside the field.
  • Resolver goldens: official capitalization and common phrases; our/their; scoring-table/non-scoring-table; near/far with and without start context; front/back/left/right at fixed, moving, and driveBackward poses; expected ambiguity cases.
  • Analysis/repair: bounded raw samples, extrema/source attribution, neutral slowdown versus measured violation, exact finding IDs, targeted candidate improvement, no worse checks, preservation of markers/actions/ranges, stale imported projects, and no silent clamping.
  • Route engine: straight, TRENCH, BUMP, out-and-back, blocked, tank versus swerve, robot too large for a portal, minimum clearance, cancellation, bounded candidate count, determinism, and no regression to existing planner IDs.
  • MCP protocol: list/read resources, list/call tools, structured outputs, annotations, cancellation, oversized inputs, app unavailable, access disabled, stale runtime descriptor, multiple clients, app shutdown, and no stdout logging corruption.
  • Java semantics: optional annotation fields generate deterministic catalogs/hashes; old annotations remain valid; ambiguous and missing capabilities never create an invocation.
  • End to end: temporary userData app instance + stdio client stages the acceptance scenario, app test clicks Apply, session reports applied revision, undo restores the fixture, and save remains user-controlled.

Non-goals for the first release

  • Parsing the game manual at runtime, relying on an external LLM/API inside Bordeaux, or treating manual prose as exact CAD.
  • Opponent prediction, multi-robot collision avoidance, live FMS data, game-rule adjudication, or claiming a globally optimal strategy.
  • Autonomous save/export/deploy, Gradle execution, arbitrary robot command inference, or direct mutation without an in-app preview.
  • Changing the geometry or timing behavior of existing planners to make route generation easier.

Recommendation summary

Build this as an app-backed authoring protocol, not a file-writing MCP server. Deliver coordinate-defined proposals first, then official 2026 vocabulary, then bounded route optimization, then team action semantics. That sequence creates a useful vertical slice early while preserving Bordeaux's file contracts, planner behavior, renderer ownership, and human review.

Statusactive · 2026-08-20

Prepare Bordeaux for WPILib Commands v3 without abandoning existing Commands v2 robots: one command-framework-neutral runtime, separate native backends, and a pinned 2027 preview track.

Verdict. Commands v3 is different enough that Bordeaux needs explicit compatibility. It is not a wrapper library and it cannot be bridged through Commands v2: WPILib's official vendordeps prohibit both frameworks in one robot project. Bordeaux should support either native framework, exactly one at a time, while keeping the normal @BordeauxCommand experience unchanged.

What this actually is

“Commands v3 from Systemcore” is the official Java-only WPILib Commands v3 framework shipping in the 2027/Systemcore software line. The latest published build reviewed for this plan is WPILib 2027.0.0-alpha-6. It is a prerelease API, and the official documentation still says the Commands v3 documentation is in progress.

This is also a broader platform boundary than a command import rename. WPILib 2027 moves Java packages from edu.wpi.first to org.wpilib and requires Java 25. Bordeaux 0.4 currently targets Java 17, WPILib 2026.2.2, and edu.wpi.first.wpilibj2.command.Command. A single binary cannot honestly cover both seasons.

Upstream is still moving after alpha-6. On WPILib main, Mechanism has already changed from a class to an interface, scheduling results changed from the released enum to a sealed hierarchy, and the Maven artifact was renamed from commands3-java to commandsv3-java. That is enough evidence to ship only pinned preview support until a 2027 beta or stable contract exists.

Current Bordeaux boundary

The command coupling is concentrated, which is good: the annotation processor hardcodes the 2026 v2 command FQN; BordeauxCommandRegistry returns v2 commands; and the event/routine runners schedule and cancel them through a v2-typed scheduler interface. Bordeaux does not inspect requirements or execute command lifecycle methods itself.

One extra coupling should be removed before the path follower lands: BordeauxDrive.requirement() returns a v2 Subsystem, although no shipped production runtime consumes it. The future follower's v2 Subsystem or v3 Mechanism belongs in the framework-specific command shell, not the drive I/O contract.

Recommended architecture

Deepen the existing seam at the only operations Bordeaux actually owns: construct one invocation, ask the native scheduler to schedule it, and request cancellation only when the provider and lifecycle make ownership of that run provable.

public interface BordeauxCommandInvocation {
    BordeauxScheduleOutcome schedule();
    void cancel();
}

public enum BordeauxScheduleOutcome {
    SCHEDULED,
    ALREADY_RUNNING,
    REJECTED
}

The exact names may change during implementation; the constraint should not. This interface must not grow fake cross-framework versions of requirements, priorities, command names, coroutine state, or group ownership. Backend-specific details can appear in diagnostics without moving their policy into core.

Each backend receives its native scheduler through construction; a production convenience may select the framework default. Generated bindings hold that backend adapter, while the neutral runtime never imports a WPILib scheduler type. An injected status sink records the event or routine-node ID, command ID, and normalized scheduling result so “rejected” is observable without GUI work.

What teams should write

The import changes with the chosen WPILib framework; the Bordeaux API does not.

@BordeauxCommand
public Command score(ScoreLevel level) {
    return superstructure.score(level);
}

@BordeauxCommand
public final Supplier<Command> intake = intakeSubsystem::intakeCommand;

A direct command field remains acceptable only for fire-and-continue use under a team-enforced mutually exclusive ownership rule. Use a supplier/factory that returns a genuinely fresh command whenever a fresh run or reliable cancelOnPathEnd ownership matters. Native schedulers cancel by command object, not by a Bordeaux run token, so successful scheduling alone cannot make a reusable field safe to cancel after another owner may have restarted it.

Behavior contract

  1. An event makes one scheduling attempt. Bordeaux does not retry an already-running or lower-priority command behind the team's back.
  2. Every attempt writes a status record with source event/node ID, command ID, and normalized outcome. A rejection does not automatically fail the path in the compatibility release; this preserves today's fire-and-continue behavior.
  3. cancelOnPathEnd requires a fresh supplier/factory command or a future proven run-token mechanism. Bordeaux must not retain cancellation ownership for an already-running or reusable shared command merely because one scheduling call succeeded.
  4. Aquitaine Command nodes remain fire-and-continue in the low-level runner and use the scheduling call site's native scope. Awaited sequencing and a parent-command shell are separately versioned features with explicit await/detach/terminal-lifetime rules.
  5. Requirements, priorities, groups, coroutine children, interruption, and completion remain native scheduler semantics. Before preview support, Bordeaux must reject new owned work while disabled, cancel all Bordeaux-owned work and safe-stop motion on robot disable, and independently verify the alpha scheduler's incomplete command-level disabled policy. An ordinary path/runner stop cancels only work explicitly owned through cancelOnPathEnd.
  6. All schedule/cancel calls occur on the scheduler's robot thread. Off-thread path generation may return data only.

Release and packaging strategy

2027 stableJava 25, stable WPILib 2027Commands v2 or Commands v3GA only after API, install, simulation, and vendor matrices pass against the released toolchain.

The logical core should stay shared, but 2026 and 2027 are separate compiled release lines because their WPILib math, geometry, units, and command packages are not binary-compatible. Do not build a reflection-heavy “universal” jar or a multi-release jar.

Within the 2027 line, publish a neutral runtime plus separate Commands v2 and Commands v3 adapter artifacts. A managed install detects CommandsV2.json or CommandsV3.json, installs exactly the matching adapter, and fails clearly when selection is missing or mixed. Initial work stays in the Java library, fixtures, documentation, and the narrow non-UI version validator required by #155; renderer and website changes are outside this plan.

Catalog compatibility

Keep command framework identity out of authored trajectory and Aquitaine schemas. Those documents already contain the correct portable contract: stable command IDs, typed arguments, conditions, and cancellation policy. Backend identity and provider-kind/cancellation eligibility belong only in generated Java bindings and .bordeaux/install.json—not authored JSON, META-INF/bordeaux/commands.json, or catalogHash. Supplier freshness remains an author contract because annotation processing cannot prove it. Changing a project's backend requires a clean rebuild of generated bindings, but should not force a GUI schema change merely because the scheduler implementation changed.

The current desktop and Java validators require one exact schema/support pair, so #155 must first introduce an explicit allowed-pairs table. Then bump the Java support version when the registry ABI changes, allow that support version with catalog schema 1.3 if the serialized shape is unchanged, and bump the schema only when its shape or authored meaning changes.

Delivery plan

  1. Pin and prove the upstream contract. Add a minimal, independent Java 25/GradleRIO fixture against one released 2027 version. Verify command construction, mandatory names, one-shot and yielding commands, schedule results, priorities, cancellation, repeated object reuse, static groups, coroutine children, opmode scope, and same-thread enforcement. Record exact artifact coordinates and commit SHA.
  2. Make command execution neutral before adding more follower coupling. Introduce the invocation/outcome seam, injected status sink, and Bordeaux-owned disabled/stop gate; move registry, event, and routine runners onto them; replace framework tests with fake invocations; preserve exactly-once events and low-level fire-and-continue routines. Remove Subsystem from the core drive contract before implementing #148.
  3. Extract the current v2 adapter. Keep 2026 behavior working through a native v2 module. Preserve annotated methods, direct fields, suppliers, and subtype validation. Require a fresh supplier/factory for reliable path-end cancellation; do not overstate ownership of a reused field. Offer a focused migration for manual registry/scheduler users instead of keeping v2 types in core.
  4. Decouple compatibility versions. Complete #155 so an explicit allowed-pairs table can admit a new Java support ABI with unchanged catalog schema 1.3 while still rejecting unknown combinations.
  5. Teach generated bindings to select one backend. The processor recognizes exact command FQNs for its release line, emits the matching adapter, accepts methods/fields/suppliers, rejects mixed frameworks, and reports a missing adapter with a direct fix. Equivalent declarations within the same 2027 Bordeaux support line produce identical semantic command catalogs and hashes.
  6. Add the native v3 adapter. Inject the native Scheduler into the adapter, with Scheduler.getDefault() only as a production convenience; pass the original v3 Command unchanged; normalize every schedule result; delegate safe cancellation; preserve the scheduling call site's scope; and prove that the adapter jar contains no v2 references.
  7. Add framework-native motion shells. Keep follower math and drive I/O in core. Add a v2 wrapper that requires the team's Subsystem and a v3 wrapper that requires its Mechanism. Before #150 claims full-auto parity, specify whether fire-and-continue children are awaited, deliberately detached, or cancelled with the parent; a parent shell must not accidentally cancel terminal commands immediately.
  8. Package and document the choice. Produce core, processor, and selected-backend artifacts; add one complete 2026 v2 fixture plus separate 2027 v2 and v3 fixtures; document direct-field ownership, suppliers, priority rejection, scopes, and coroutine hazards. Backend detection in managed project installation is coordinated later without renderer or website work.
  9. Promote only on evidence. Re-run the full matrix on each 2027 beta and the stable release. Add Commands v3 to the public compatibility table only after #153 passes simulation, install, and vendor-command interop gates.

Verification matrix

  • Neutral core: runtime tests pass with neither command framework on the classpath; jdeps and jar inspection find no command2, command3, Subsystem, or Mechanism references.
  • 2026 v2: Java 17/WPILib 2026 fixture covers method, direct field, fresh supplier, schedule, cancel, already-active ownership, event repetition, safe path-end cancellation, a reused field restarted by another owner, and Aquitaine fire-and-continue.
  • 2027 v2: Java 25/WPILib 2027 fixture compiles and runs with Commands v2 only, proving the package migration independent of v3.
  • 2027 v3: separate fixture covers the supported release's complete schedule-result model, equal/higher/lower priority conflicts, one-shot commands, yielding loops, onCancel, injected/default schedulers, global/opmode/parent call-site scope, opmode exit, group behavior, disabled transitions, and repeated instance reuse.
  • Processor: compile tests cover exact FQNs, subtypes, methods, fields, suppliers, nulls, missing backend, mixed framework, generated-source compilation, Java 25, and coexistence with WPILib's compiler plugin.
  • Catalog: equivalent v2/v3 declarations within the same 2027 support line produce identical capability JSON and semantic hashes; backend identity appears in generated bindings and .bordeaux/install.json only. Switching backend forces both to regenerate.
  • End to end: install → annotation processing → catalog → export → deploy-file read → event/routine execution → status record → cancellation passes once per fixture without loading the other framework; disable rejects new owned work, cancels owned work, and safe-stops motion.
  • Vendor commands: PathPlanner, Choreo, SysId, and vendor-generated command examples are certified independently. A library that only returns v2 commands is not compatible with a v3-only robot until that library publishes native v3 support.

Decisions and gates

  • Decision: support Commands v3 natively; do not replace or abandon Commands v2.
  • Decision: exactly one command framework per robot project.
  • Decision: keep the Bordeaux catalog and authored trajectory schema command-framework-neutral.
  • Decision: require a fresh supplier/factory for reliable cancelOnPathEnd; direct reusable fields are fire-and-continue under team-owned exclusivity.
  • Decision: inject the native scheduler and preserve the scheduling call site's native scope; use the default scheduler only as a convenience.
  • Decision: report and continue on schedule rejection in the compatibility release; do not retry or invent priority policy.
  • Decision: ship v3 as preview while upstream remains alpha.
  • Beta gate: freeze exact FQNs, artifact coordinates, Mechanism shape, scheduler outcomes, module-open behavior, and compiler-plugin requirements against the first supported 2027 beta.
  • Safety gate: verify the supported v3 release's command-level disabled semantics while independently proving Bordeaux motion always stops and zeros safely on disable.
  • GA gate: pass the independent fixtures, full runtime lifecycle, managed install, and vendor-command matrix on stable WPILib 2027.

Non-goals

  • Load Commands v2 and v3 in the same robot, translate Subsystem into Mechanism, or wrap one scheduler inside the other.
  • Reimplement WPILib requirements, priority arbitration, coroutine execution, groups, triggers, or opmode scoping.
  • Declare stable Commands v3 support against an alpha API or claim vendor-command compatibility without a pinned compile/runtime fixture.
  • Modify the Bordeaux renderer, GUI, website, or path-authoring schemas during the initial Java compatibility work.

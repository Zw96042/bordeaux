Path and routine library with quick push

Projectbordeaux
Versionv2
Statusdone · 2026-09-04

Replace the temporary path and routine pickers with a persistent library beside the editor, and let users push the item they are working on without leaving it.

The owner clarified that “switch paths” means switching what is edited and sent, not selecting what the robot will execute. The owner subsequently approved implementation. The desktop library, scoped snapshot composition, and versioned runtime baseline-read capability are now implemented in the working tree. Robot execution selection remains outside this workflow.

Product contract

  • One home for the collection. A library with Paths and Routines tabs handles browsing, search, folders, and item actions. Selecting an item opens its existing editor immediately.
  • Stay in the editor. The field remains visible while switching and managing items. There is no separate Deploy workspace.
  • Push has explicit scope. “Push path,” “Push 3 paths,” and “Push routine” refer to named, frozen selections. Browsing another routine never changes an in-flight operation or the routine preserved on the robot.
  • Preserve other robot content. A path update replaces or adds only the chosen paths in a complete robot revision. It preserves other paths and the existing routine. A local delete never deletes robot content.
  • Keep the robot contract. Saving remains local. Push is explicit, paired, validated, atomically staged, and activated only while disabled, with robot acknowledgment. Upload completion is not acceptance or execution.

Success is a short loop: select a path → edit → review the named update → push → see acceptance → select the next path. The normal paired case takes two deliberate actions after editing: Push path, then confirmation in a compact review.

Workspace organization

  • Navigation: Paths and Routines become the editor-mode switch. Remove the redundant Plan/Aquitaine toolbar switch and both modal library triggers once this surface replaces them. Retain Aquitaine as the routine editor’s name, existing internal routes, and a separate Robot settings entry. Returning from Robot restores the last editor selection.
  • Left rail: start around 280–300 px, with independently scrolling library and structure sections and an adjustable vertical divider. Either section can collapse; remember its size, query, folder expansion, and scroll position per project and tab. Do not persist these preferences into executable export identity.
  • Item rows: name first, compact duration or step count second, and a text-accessible push state. Highlight the item being edited; use separate checkboxes in explicit batch-selection mode. Checking a box does not open that item or change the push target while a review is open.
  • Selected-item header: full name, readiness/status, and one primary scoped push action. Row menus can offer Push for convenience through the same controller, rather than creating independent flows.
  • Small windows: keep the docked rail within the supported desktop window range, narrowing it below 1200 px. The field, structure and inspector remain usable in captured 1440, 1280 and 1024 px layouts; the desktop minimum is 1100 px. A drawer is deferred until a smaller supported window needs it. Both rail sections can collapse.
  • Global controls: Save/Open and document actions remain reachable in both editor modes. The robot indicator opens connection, revision history, rollback, and diagnostics. Export JSON remains a secondary file action with its scope named, separate from sending data to the robot.

Push flow and content rules

  1. Capture intent. Resolve current editor changes and capture a materialized project plus explicit path IDs or routine ID. Do not infer the routine from whichever tab happens to be open.
  2. Prepare. Verify the paired robot, inspect its active revision, obtain the verified baseline, and compile only the selected local content and required dependencies. Keep planning in the existing worker boundary.
  3. Review inline. Show target robot, selected names, paths added/updated, impacted preserved routine, and any dependency expansion. Make “other paths and routine preserved” concrete with a count/name. Technical IDs live under details. First-time pairing replaces this step until setup succeeds, then resumes the same captured intent.
  4. Confirm and send. Use the existing immutable-operation confirmation. Editing or navigating afterward does not change the reviewed bytes. Show that newer edits remain local; invalidate the review if its project, pairing, or Java catalog context changes.
  5. Acknowledge. Show accepted only for the exact reviewed revision. Keep progress accessible when the user switches items or closes the progress surface. After staging, closing the surface must not imply canceling the robot request.

There is no robot run/chooser control in this work, no automatic push on save, and no multi-routine robot catalog. Remote item deletion, automatic syncing, multi-robot fleet management, and bulk routine pushes are outside this plan.

Implementation architecture

Keep full immutable revisions as the transfer unit. “Push path” describes the logical change, not a promise to transfer only one path’s bytes. Compose a complete snapshot on the desktop, then reuse expected-active-revision checks, staging, disabled-only activation, acknowledgment, retention, and rollback. A new delta-write protocol is not the default approach.

  1. Verified baseline read: add a bounded desktop transport operation for the active retained revision/payload. The Java state directory is configurable: negotiate a supported read location/capability instead of guessing its private filesystem path. Within that contract, derive reads from validated revision IDs, never arbitrary renderer paths. Verify pairing/runtime identity, payload hash and derived revision identity, schema, limits, and that the inspected active revision matches the payload. Retained storage currently contains the trajectory payload, not the original activation envelope. Recheck status after reading; activation’s expected revision remains the final concurrency guard. Missing/rotated baseline, unsupported retention, malformed data, and unknown versions fail closed.
  2. Scoped compilation and snapshot composition: introduce an explicit request union for selected path IDs or one routine ID. Reuse existing generation and validation logic; scope authoring validation so an unrelated broken draft does not block a valid selected update. Then validate the entire composed executable snapshot, including preserved items, dependencies, identity, names/IDs, counts, and byte limits. Preserve unchanged exported records without regenerating them from local drafts.
  3. Shared context: baseline and selected content must agree on field, catalog/support identity, units, and exported robot configuration. A global configuration change requires explicit full replacement/rebuild; do not transplant old samples into a new robot context. Path names remain user-facing, but stable IDs govern replacement. Reject name ambiguities that would break Java name-based lookup.
  4. Single push controller: move operation state out of the modal-only component into an app-owned controller. Library/header actions submit an explicit scope; connection/history and review/progress surfaces consume the same state. Retain the existing paired connection and transport mechanisms.
  5. Project and operation boundaries: associate local receipts with project provenance, paired robot/runtime, catalog, base/result revision, explicit IDs, and exact compiled fingerprints. The current payload has no project identity or routine ID. Do not infer either from display names. A first encounter with an unassociated baseline requires an explicit adoption/replacement review; a stale local cache alone cannot establish current robot contents. Adoption associates a baseline with this project, not a routine ID inferred from its name. Exact compiled graph and dependency comparison can prove content equivalence; verified local receipts can map a local routine ID to accepted contents. Otherwise the routine relationship remains unknown.

The baseline-read prototype must prove that existing retained storage provides a stable, bounded read contract. If it does not, add a small versioned read capability/status descriptor in the Java runtime and gate selective push on that capability. Do not broaden the write/activation protocol merely to expose this read.

Use two separate facts: local readiness and relationship to the inspected robot revision. A compile error can coexist with “last accepted yesterday.” Do not overload a single green dot.

Implement in cohesive phases. Phases 1 and 2 establish the UI and data contract; selective push becomes available only after preservation and acknowledgment tests pass. The owner approved these phases for implementation after reviewing the plan.

  1. Library layout and switching. Extract the two libraries from Panels.jsx into a focused shared shell with distinct path/routine content. Integrate it with the existing outline, routine panel, inspector, and selection callbacks. Preserve search, folder and action functionality; add stable-ID batch selection. Check real desktop widths and narrow-window behavior. Keep any intermediate legacy push explicitly labeled as whole-project scope.
  2. Selective snapshot foundation. Prove bounded baseline reads with transport fixtures, define request/preview types, implement scoped compilation and complete-snapshot composition, and cover empty, incompatible, changed, and missing baselines. Decide whether the Java read capability is necessary from that proof. No selective button ships ahead of this contract.
  3. Quick push and robot surface. Wire selected path, path batch, and routine actions into the app-owned controller. Replace the sprawling modal with compact review/progress and secondary connection/history surfaces. Preserve pairing, pin, rollback, diagnostics, and existing immutable confirmation semantics.
  4. Status and recovery. Add per-item comparison/receipts, context invalidation, offline/unknown states, and acknowledgment reconciliation. Verify that switching during upload keeps the original target and that later edits remain marked local.
  5. End-to-end polish and release check. Remove superseded navigation and duplicate push entry points, update user/runtime docs where contracts changed, complete accessibility and large-library checks, and run an independent correctness and UI review. Resolve blocking findings before shipping.

Implementation results

The persistent library now owns Paths/Routines switching, search, folders, stable-ID batch selection, item actions, and a shared adjustable rail with the existing structure panels. A single application-owned controller handles scoped review, pairing, immutable confirmation, progress, history, pin, rollback, and diagnostics.

Selective pushes compose complete snapshots from a bounded, hash-verified active payload exposed by the runtime under bordeaux-active-revision/1.0. Full generation-context fingerprints prevent mixing old trajectories with changed robot settings. Local receipts bind comparisons to project and runtime identity; stale or unassociated content remains Unknown. Explicit routine pushes include the full linked-path dependency closure.

Older runtimes require updated Java support before selective baseline reads. Older snapshots without a generation-context fingerprint require one explicitly reviewed full-project replacement. The current runtime payload requires at least one static path, so a command-only routine cannot be the first push to an empty robot; the UI reports the prerequisite.

Verification and independent review results are recorded in the companion implementation review. All 658 unit tests, Java tests, type checks, renderer checks, 10 library UI scenarios, 21 controller checks, and integrated Electron smoke passed. No physical robot was contacted. Real-hardware disabled activation and acknowledgment remain deployment validation, not an outcome claimed by this task.

Boundaries

The implemented product direction is persistent library, fast local switching, scoped push, and preserved robot content. Baseline reads are a versioned runtime capability; the existing immutable write and activation protocol is retained.

This plan does not change planner algorithms, robot execution selection, drivetrain behavior, file export formats incidentally, or the single-routine runtime model. It preserves the explicit data-push and activation boundary in the existing Bordeaux product scope contract. The working tree contains extensive unrelated ongoing work; implementation must establish a fresh baseline and keep its changes focused.

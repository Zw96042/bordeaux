Editing Overlapping Visits in One Path

Projectbordeaux
Versionv4
Statusactive · 2026-08-04

Make overlapping passes selectable as distinct ordered visits, then keep every edit latched to the chosen visit without moving the authored geometry.

Context

A single Bordeaux path can cross the same field location several times. Those strokes may be visually identical while representing different segments, distances, times, headings, velocities, constraints, targets, or markers.

The current editor collapses that distinction in two places: SVG hit paths resolve by paint order, and nearestFraction returns one globally nearest sample. The result is unpredictable selection, constraint endpoints that can jump between passes, and coincident handles that steal pointer input from one another.

Constraint: this must work inside one ordered path. The primary workflow cannot require duplicate paths, permanent visual offsets, or a persisted layer taxonomy.

Recommendation

Implement visit-aware focus with conflict cycling. A visit is one occurrence of the trajectory at a field location, identified by ordered path distance and segment-local position. The pointer resolver returns every nearby visit, the user focuses one when there is a conflict, and drag operations remain latched to it.

ResolveFind every nearby visit, not one global nearest point.
→
FocusSelect one visit; cycle only when the location is ambiguous.
→
LatchKeep constraints, markers, targets, and handles on that visit.

Simple paths retain the current one-click workflow. Only an actual overlap introduces a compact 1 of N visits affordance, keyboard cycling, and muted competing hit areas.

Interaction contract

  • Clicking an unambiguous stroke behaves exactly as it does now.
  • At a conflict, the closest visit is focused; repeated click, [/], or previous/next controls cycle deterministically.
  • The focused visit uses the normal accent. Coincident alternatives stay visible, become pointer-inert, and never change overlay color semantics.
  • Selecting a segment, waypoint, constraint, target, or marker in the outline restores its visit focus on the field.
  • Escape clears focus. Focus is transient editor state and is not serialized or exported to .bdx.

Technical design

Candidate resolver

Add a pure geometry helper that projects the pointer onto sampled polyline edges, not only sample points. It returns candidates containing screen distance, ordered path distance/fraction, segment index, and local segment parameter.

  1. Project onto every edge inside a screen-pixel tolerance so behavior stays stable across zoom levels.
  2. Cluster adjacent samples that describe the same visit.
  3. Keep candidates separate whenever their ordered path distances differ, even when field coordinates and segment index match.
  4. Rank by screen distance, existing visit/segment affinity, then path order for deterministic ties.

Latched editing

On pointer-down, resolve a candidate tuple such as {segment, localT, distance}. During the drag, project against candidates nearest the previous ordered distance and use hysteresis to prevent branch changes. A user must cycle or restart the drag to intentionally switch visits.

Use the same projection for constraint endpoints, rotation targets, event markers, explicit insertion, and path scrubbing. Existing proportional and segment-local storage remain unchanged; visit-aware projection only chooses the correct fraction.

Coincident controls

Render the selected waypoint and its tangent handles last. When visit focus exists, competing coincident hit areas become inert while their geometry remains visible. Handles always stay in true field coordinates; no editing offset is introduced.

Implementation steps

Phase 1

Visit selection. Add and unit-test nearestVisits; introduce transient activeVisit; add conflict cycling; route segment selection, insertion, target placement, and marker placement through the chosen visit.

Phase 2

Stable feature drags. Latch constraint, rotation-target, and event-marker drags to one candidate; add continuity-aware projection and hysteresis; verify proportional and segment-local anchors through edits and reversal.

Phase 3

Coincident controls. Render selected nodes last, suppress competing hit areas, add waypoint cycling, and synchronize outline selection with field focus.

Phase 4

Optional inspection. Evaluate a compact sequence strip and read-only spread-visits view. Add persisted named layers only if real routines prove automatic focus insufficient.

Implementation result

Core interaction shipped

The field now resolves every nearby ordered visit, highlights the active pass, cycles conflicts with repeated click or [/], and restores focus from selected segments, features, and coincident waypoints.

Edits stay latched

Constraint endpoints, new ranges, rotation targets, event markers, and explicit insertion carry the chosen path fraction through placement and drag projection. The focus remains transient and does not alter project or .bdx serialization.

Validated

Exact retraces, coincident Start/End cycling, and selected-node dragging were exercised in the running editor. The renderer verification, 142-test suite, TypeScript checks, production build, and Electron smoke test pass; an independent read-only review found no remaining overlap-editing blocker. Phase 4 remains intentionally optional until real routines show that automatic focus needs a timeline accelerator.

Verification

  • Pure resolver tests cover exact retraces, same-segment self-intersection, adjacent sample clustering, and stable path ordering.
  • Running-editor checks confirm retraced visits can be selected and cycled, outline selection restores coincident waypoint focus, and the selected coincident waypoint drags without moving its neighbor.
  • Renderer regression checks assert that constraint, rotation-target, event-marker, and insertion placement carry the selected visit fraction or local parameter.
  • A continuous constraint or feature drag projects by its previous path fraction, preventing a normal drag from jumping to another visit.
  • Non-overlapping paths retain the current one-click behavior with no conflict UI.

Open questions

The owner choice attached to this plan asks whether visit-aware focus should lead, or whether Bordeaux should accept the permanent UI or project-structure cost of a timeline-first or manual-layer model. The recommendation is visit-aware focus first, with a sequence strip as a later accelerator for long routines.

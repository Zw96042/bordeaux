Java command events are practical, but the safe Java equivalent of a LabVIEW VI reference is a stable command ID resolved by robot-owned factory code—not a serialized class, method, or object reference.

Approved direction, full scope now active. The app-first milestone is complete. The current implementation extends the same stable-command-ID and JSON invocation contract through annotated team-owned factories, a generated catalog and compile-time bindings, trusted catalog builds, native Java trajectory export, and a WPILib event runner. PathPlanner and Choreo remain out of scope because the native contract does not need either adapter.

Feasibility and the important difference from LabVIEW

Yes, the end-to-end behavior is possible in Java: discover callable robot actions, show them in Bordeaux, attach an action and parameters to a trajectory event, then execute it when the trajectory reaches that event. WPILib already provides the runtime half: commands are scheduled and run synchronously through CommandScheduler, which also arbitrates subsystem requirements and interruptions. The scheduler normally runs once per robot loop, commonly every 20 ms. WPILib command scheduler documentation

The part that does not transfer from LabVIEW is reference identity. A VI reference is meaningful to the LabVIEW application and runtime that opened it. A Java object, lambda, Method, or method handle is likewise meaningful only inside the JVM that created it; Bordeaux is an Electron process on the development computer and the robot is a different JVM on a different machine. Java serialization cannot turn that live reference into a safe cross-process capability, and a fully qualified class name does not solve constructor dependencies, subsystem ownership, or parameter meaning.

The cross-process contract should therefore be:

trajectory event = stable command ID + typed argument values + event time
robot registry   = stable command ID -> factory(arguments) -> fresh WPILib Command
robot scheduler  = schedule(command) when the event time is crossed

This follows common command-based robot structure: commands often receive subsystem dependencies through constructors or factory methods, and subsystem requirements are enforced by the scheduler. WPILib subsystem documentation

Approved first milestone

  • Project discovery: explicitly link a GradleRIO/Java project, scan bounded Java source roots automatically, retain session/recent project state, and refresh without executing robot code or Gradle tasks.
  • Command discovery: recognize concrete WPILib command classes and command-returning factory methods, including constructors/factories with primitive, enum, collection, record, and custom Java parameters.
  • Custom data types: preserve the Java type name and build nested schemas for records, enums, arrays/collections, maps, optionals, and discoverable constructor-shaped classes. Unknown types remain editable as validated JSON rather than being discarded.
  • Authoring UX: replace the hardcoded command list with linked-project status, refresh/error states, searchable commands, nested parameter controls, defaults, and an explicit raw-JSON fallback for opaque custom types.
  • Project persistence: store stable command IDs and JSON-compatible arguments on markers additively. Existing projects and LabVIEW binary output remain unchanged.
  • Not in this milestone: robot execution, command scheduling, vendor dependency distribution, annotations supplied by Bordeaux, deploy-folder writes, PathPlanner/Choreo compatibility, and a final Java trajectory export contract.

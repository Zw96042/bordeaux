Projectbordeaux
Versionv5
Statusactive · 2026-08-05

Java command events are practical, but the safe Java equivalent of a LabVIEW VI reference is a stable command ID resolved by robot-owned factory code—not a serialized class, method, or object reference.

Approved direction, full scope now active. The app-first milestone is complete. The current implementation extends the same stable-command-ID and JSON invocation contract through annotated team-owned factories, a generated catalog and compile-time bindings, trusted catalog builds, native Java trajectory export, and a WPILib event runner. PathPlanner and Choreo remain out of scope because the native contract does not need either adapter.

Feasibility and the important difference from LabVIEW

Yes, the end-to-end behavior is possible in Java: discover callable robot actions, show them in Bordeaux, attach an action and parameters to a trajectory event, then execute it when the trajectory reaches that event. WPILib already provides the runtime half: commands are scheduled and run synchronously through CommandScheduler, which also arbitrates subsystem requirements and interruptions. The scheduler normally runs once per robot loop, commonly every 20 ms. WPILib command scheduler documentation

The part that does not transfer from LabVIEW is reference identity. A VI reference is meaningful to the LabVIEW application and runtime that opened it. A Java object, lambda, Method, or method handle is likewise meaningful only inside the JVM that created it; Bordeaux is an Electron process on the development computer and the robot is a different JVM on a different machine. Java serialization cannot turn that live reference into a safe cross-process capability, and a fully qualified class name does not solve constructor dependencies, subsystem ownership, or parameter meaning.

The cross-process contract should therefore be:

trajectory event = stable command ID + typed argument values + event time
robot registry   = stable command ID -> factory(arguments) -> fresh WPILib Command
robot scheduler  = schedule(command) when the event time is crossed

This follows common command-based robot structure: commands often receive subsystem dependencies through constructors or factory methods, and subsystem requirements are enforced by the scheduler. WPILib subsystem documentation

Approved first milestone

  • Project discovery: explicitly link a GradleRIO/Java project, scan bounded Java source roots automatically, retain session/recent project state, and refresh without executing robot code or Gradle tasks.
  • Command discovery: recognize concrete WPILib command classes and command-returning factory methods, including constructors/factories with primitive, enum, collection, record, and custom Java parameters.
  • Custom data types: preserve the Java type name and build nested schemas for records, enums, arrays/collections, maps, optionals, and discoverable constructor-shaped classes. Unknown types remain editable as validated JSON rather than being discarded.
  • Authoring UX: replace the hardcoded command list with linked-project status, refresh/error states, searchable commands, nested parameter controls, defaults, and an explicit raw-JSON fallback for opaque custom types.
  • Project persistence: store stable command IDs and JSON-compatible arguments on markers additively. Existing projects and LabVIEW binary output remain unchanged.
  • Not in this milestone: robot execution, command scheduling, vendor dependency distribution, annotations supplied by Bordeaux, deploy-folder writes, PathPlanner/Choreo compatibility, and a final Java trajectory export contract.

Proposed three-plane architecture

The catalog is the editor-facing truth and the registry is the runtime-facing truth. Both carry the same stable IDs and schema version. A hash recorded in the trajectory lets the runtime detect a stale or mismatched pairing instead of silently invoking the wrong behavior.

Command catalog and trajectory contracts

Catalog

{
  "schemaVersion": "1.0",
  "catalogId": "frc-9999-2027-robot",
  "commands": [
    {
      "id": "superstructure.score",
      "label": "Score game piece",
      "description": "Moves to a scoring level and releases",
      "parameters": [
        { "key": "level", "type": "enum", "values": ["L1", "L2", "L3", "L4"], "default": "L4" },
        { "key": "releaseDelayS", "type": "number", "unit": "s", "min": 0, "max": 1.5, "default": 0.1 }
      ]
    }
  ]
}

The schema must support both scalar and custom Java types. Scalars include boolean, integer, finite number, string, and enum. Structured values include records/objects, arrays and collections, maps with string keys, and optionals/nullability. A schema retains the fully qualified Java type name and recursively describes discoverable fields. An opaque custom type uses a JSON editor with parse validation and a visible “runtime conversion not yet defined” warning. Subsystem objects, command instances, suppliers, method references, and Java expressions are dependencies—not authored parameter values.

Authored marker and exported invocation

// Optional and additive in the Bordeaux project model
marker.invocation = {
  "commandId": "superstructure.score",
  "arguments": { "level": "L4", "releaseDelayS": 0.15 }
}

// Fully resolved in the Java deploy artifact
event = {
  "eventId": "evt_2f11...",
  "timeS": 2.84,
  "commandId": "superstructure.score",
  "arguments": { "level": "L4", "releaseDelayS": 0.15 }
}

Keep commandId stable even when the display label changes. Give every event a stable ID so the runner can provide exactly-once behavior per autonomous run. Preserve legacy cmd strings during migration; if a string matches a catalog ID it can be upgraded with empty/default arguments, while unknown strings remain visible and block Java export until resolved.

Future robot-side API and execution semantics

This section defines the later JSON/runtime boundary; it is intentionally not implemented in the approved app-first milestone.

public final class RobotContainer {
  private final BordeauxRegistry bordeaux = new BordeauxRegistry();

  public RobotContainer() {
    bordeaux.register(
        "superstructure.score",
        ScoreParams.SCHEMA,
        args -> superstructure.score(args.enumValue("level"), args.number("releaseDelayS")));
  }
}

// Called from the trajectory follower's normal periodic update.
eventRunner.advance(previousElapsedS, currentElapsedS, bordeaux, Command::schedule);

The factory is robot code, so it naturally captures the team's real subsystem instances and may return a class-based command, a subsystem factory command, a lambda-built command, or a composition. This is why a registry works for modern WPILib projects even when no discoverable Command subclass exists. WPILib explicitly supports inline factories, lambdas, method references, and command compositions. WPILib command-based overview

The event runner should:

  • On every robot update, run any unfired event whose condition is already satisfied—initially currentTime >= event.timeS. A fired-event set provides exactly-once behavior, so loop jitter cannot skip a timestamp. A WPILib periodic callback or equivalent main-loop update is sufficient; no equality check or special LabVIEW-style Timed Loop primitive is required.
  • Fire all crossed events in stable time/file order after a loop overrun or time jump rather than requiring equality with a 20 ms tick.
  • Reset its fired-event set only when the autonomous run restarts; never refire due to repeated samples or clock jitter.
  • Validate the entire file, catalog ID/hash, command IDs, and parameters before the path begins. Fail closed with a precise Driver Station error rather than discovering a mismatch halfway through auto.
  • Let CommandScheduler own normal subsystem conflict and interruption behavior. Two commands requiring the same subsystem cannot safely run concurrently. WPILib Command API
  • Define path-cancellation ownership explicitly: v1 should schedule events without pausing trajectory time; on path interruption, cancel only commands explicitly marked as path-owned.
Do not reuse the current “sequential / parallel / deadline” labels without a formal contract. For a detached time marker, “sequential” could mean pause the path, “deadline” could mean cancel at path end, and “parallel” could mean ordinary scheduling. Those choices have different timing and safety effects. Preserve the old field for compatibility, but v1 Java events should expose one unambiguous “schedule on crossing” behavior plus an optional “cancel on path end” ownership flag. Add pause/zone/deadline semantics only with dedicated lifecycle tests.

Prioritized findings

P2 marks material repeated work or a scalability concern; P3 marks a narrower improvement or maintenance risk. Source-demonstrated work is distinguished from measured user impact.

Q01 · P2 · Stop serializing the whole trajectory library during one-path edits

src/renderer/app/App.jsx:786-790; src/shared/planners/acceptedTrajectoryIdentity.ts:22-37

Every project.paths replacement rebuilds durationInputs for all paths. Each applied path computes its physical key twice, then JSON-stringifies the entire accepted result. The current-path outdated check also recomputes a key already memoized in App. This makes a local edit pay for unrelated library content.

Evidence: Measured the exact durationInputs expression with real accepted slalom trajectories: 6.67 ms for 20 paths; 33.82 ms for 100 paths, producing 12.2 million key characters. These are Node microbenchmarks, not measured React-frame latency.

Focused change: Reuse the computed physical key, keep per-path entries stable for unchanged path/robot/field inputs, and compare the immutable accepted artifact separately by identity. Do not use only inputKey: replacing an artifact with different output under the same inputs must invalidate its duration.

Verification: Count key computations for a one-path edit; unchanged entries should retain their results. Verify new artifacts, robot/field changes, stale inputs and corrupt accepted output still invalidate or fail closed.

Q02 · P2 · Do not construct and broadcast an unchanged optimizer preview

src/shared/planners/corridorFinal.ts:345,381-384; src/renderer/assets/path-preview-worker.js:271-285; src/renderer/assets/path-optimization.js:33-36

Every candidate evaluation, including rejection, emits the best-so-far trajectory. The worker derives and projects a complete preview, transfers it, and the controller updates App state. The progress state itself has no renderer consumer. The final-planning controller does retain an incumbent for timeout recovery, so progress cannot simply be deleted.

Evidence: Actual slalom optimization produced 25 callbacks for 24 evaluations, with 16 callbacks repeating the same sample array and only 9 distinct arrays. The cost of projection/IPC and its effect on the search budget remain unmeasured. Progress projection runs within the wall-clock search budget but outside the recorded candidate evaluation duration.

Focused change: Emit full incumbents initially and when the best trajectory changes. Avoid putting unread preview payloads in App state. Preserve timeout/cancel recovery; if final evaluation counters matter, send lightweight statistics separately rather than projecting the unchanged route.

Verification: Assert callback counts track changed incumbents, and verify timeout/cancellation still returns the last validated candidate. Compare optimizer result correctness and completed evaluation counts under the same budget.

Q03 · P2 · Avoid full-project agent synchronization when it has no consumer

src/renderer/app/App.jsx:649-680; src/electron/preload.ts:86; src/electron/agentSession.ts:313-316

Project and active-path changes schedule an agent snapshot after 150 ms or on pointerup, including when MCP is disabled. The renderer first JSON-clones the whole project, IPC copies it again, and the main process validates every path. This synchronization is independent of normal saving.

Evidence: For a valid 100-path project with real accepted artifacts, the extra JSON clone alone measured 52.00 ms median; main-process validation measured 4.45 ms. IPC transfer and end-to-end interaction latency were not measured. At 20 paths the clone measured 10.37 ms.

Focused change: Give agent synchronization a clear enabled/ready lifecycle and remove the redundant JSON clone after verifying the structured-clone contract. Enabling must publish a current snapshot before requests use it; disabling must cancel or invalidate stale session work. Do not merely gate publication while leaving an old snapshot callable.

Verification: Exercise disabled editing, enable-after-edit, rapid enable/disable, proposal staleness and in-flight cancellation. Confirm current immutable project data crosses IPC without the preliminary JSON round trip.

Q04 · P2 · Skip unchanged document replacement during autosave

src/electron/projectFiles.ts:315-377; src/electron/main.ts:673-688

Each autosave serializes every path/routine, reads and hashes all managed documents, writes the workspace journal, rechecks each existing file and replaces it even when desired content equals observed content. The project also passes through encodeProjectFile where only the normalized project is needed. The two workspace writes serve recovery and should not be removed merely as duplication.

Evidence: A real persistence probe in an isolated task folder renamed one path in a 20-path project. All 20 remaining unchanged documents were replaced, confirmed by changed inodes with byte-identical contents. That single save took 11.28 ms on local storage; no general disk-latency claim is made.

Focused change: Skip replacements whose verified current hash equals the desired hash, accounting for case-only aliases and pending recovery ownership. Keep conflict detection and journal ordering. Separately consider a normalize/validate operation that does not build discarded JSON; do not remove validation from recovery loading.

Verification: Assert unchanged file identity/mtime survives a one-document change, then exercise external edits, case renames, partial writes, legacy recovery and queued saves. This is persistence-sensitive work despite the small proposed fast path.

Q05 · P3 · Keep immutable accepted artifacts out of per-frame deep copies

src/renderer/app/App.jsx:804-830; src/shared/project/defaults.ts:36-38; src/renderer/components/FieldView.jsx:256-261

Field dragging is already coalesced to animation frames, but mutate JSON-clones the complete path each frame. Its accepted trajectory remains attached even after authored geometry changes. History also stores deep copies up to 80 entries. This spreads large immutable output through the edit representation.

Evidence: The corpus slalom accepted artifact is 120,477 bytes and 449 samples; cloning its whole selected path measured 0.51 ms median. That fixture does not demonstrate a dropped frame by itself. The concern grows with artifact size, other frame work and retained history.

Focused change: Use an edit-copy operation that copies mutable authored data while retaining the immutable accepted artifact by reference. Audit all mutation paths before relying on sharing, and preserve the old artifact for undo and stale-optimization display.

Verification: Freeze a retained artifact and run waypoint edits, apply/use-normal actions, cancel, undo/redo and save/reload. Verify authored inputs change without altering the retained trajectory and profile a dense accepted path.

Q06 · P2 · Separate routine playback pose updates from static route geometry

src/renderer/app/App.jsx:157-161; src/renderer/lib/routineModel.js:334-351; src/renderer/components/FieldView.jsx:939-987

RoutineFieldPlayback creates a new overlay at every playback time. fieldOverlay maps each segment into new descriptors even when their done/active/pending states are unchanged. That invalidates FieldView’s routineLayers memo and sorts segments and formats every sampled point into SVG path strings again each frame.

Evidence: Coordinator-traced live call path; frame timing not measured. Existing binary-search tests for pose/step lookup pass, but they do not cover SVG reconstruction. Cost is proportional to all displayed route points per tick, not just the robot pose.

Focused change: Build geometry strings from stable path points and viewport inputs. Change segment styling when the active step/status changes; let the robot pose continue updating each frame. Preserve hit targets, overlapping-path ordering and generated-path styling.

Verification: Count geometry construction while advancing time within one step: no repeat work unless geometry or viewport changes. Then inspect playback across step boundaries, selection, zoom/pan and both supported window sizes.

Q07 · P3 · Give final-planning result interpretation one owner

src/renderer/hooks/useRoutinePlanning.js:29-43; src/renderer/lib/libraryDurations.js:28-31; src/renderer/app/App.jsx:208,792

Editor, routine and library consumers each interpret success/failure and whether a current applied artifact was validated, with different error fallbacks. They also omit field in requests where PathOptimization passes it. A maintainer changing this contract must update several independent conditions and messages.

Evidence: Duplication and field omission are source-confirmed. A non-default-field failure is latent, not currently reachable through normal project loading: fileFormat.ts rejects other field identities. This is a maintenance finding, not evidence of a current wrong-field export.

Focused change: Use one small result interpreter for validated selected trajectories, status and user-facing failure text, then make request context explicit. Keep editor provisional-preview behavior and routine/library ready-state behavior distinct where they genuinely differ.

Verification: Test malformed output, ordinary success, accepted current/stale/corrupt output, cancellation and timeout through consumer behavior. Verify field reaches the worker without weakening the supported-field boundary.

Q08 · P3 · Use a bounded-distance query for the corridor membership predicate

src/shared/planners/corridorFinal.ts:99-115,372; src/shared/planners/acceptedTrajectory.ts:78

The corridor check asks whether each footprint vertex lies within a distance threshold, but distanceToRoute computes the exact minimum across every reference edge. Every candidate and accepted-output validation repeats samples × footprint vertices × reference edges work.

Evidence: The nested full scans and call sites are source-confirmed; relative runtime contribution is not measured. With comparable sample/reference density this can scale quadratically with path length. Early rejection already exists at outer every calls; the unnecessary inner exact-minimum scan remains.

Focused change: Use an existential edge-within-threshold query that stops on a qualifying edge. Any locality hint must still fall back to all relevant edges so self-crossing paths remain equivalent. Measure before introducing a spatial index or larger framework.

Verification: Compare accept/reject results against the current exhaustive reference over the corpus, self-crossings, exact-boundary points, repeated points and varied footprints. Then measure edge visits and runtime before prioritizing more infrastructure.

Code-quality judgment and implementation order

The issue is not simply that App and main are large. Large immutable trajectory outputs are repeatedly handled as ordinary editable data, and final-planning validity is interpreted in several places. Clearer ownership of those two concerns would reduce both runtime work and the number of callers that must change together. Extracting forwarding hooks or adding broad caching would not solve those problems.

Start with duration identity (Q01) and optimizer progress (Q02), then redundant agent copying (Q03). Follow with immutable edit/history sharing (Q05) and unchanged persistence writes (Q04), preserving their behavioral boundaries. Profile routine rendering (Q06) and consolidate the demonstrated result contract (Q07). Benchmark the corridor predicate (Q08) before pursuing a larger algorithm change.

Additional profiling lead

FinalPlanning creates and terminates a module worker per request. Library and routine planning therefore pay sequential worker startup costs per path. This lifecycle is source-confirmed; its material cost is not measured, so a worker pool is not a recommended immediate change. The second editor planner is enabled only for a current accepted optimization while its comparison panel is open; it does not run unconditionally on every edit. If measurement justifies reuse, cancellation/timeouts must still terminate synchronous jobs.

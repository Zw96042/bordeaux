Bordeaux has a solid security and compatibility foundation, but this worktree is not ship-ready: one P0 branding-contract regression, three confirmed planner/resource defects, a renderer crash, and robot-runtime scaling risks must be resolved before lightweight cleanup is treated as cosmetic optimization.

Verdict: hold release. All 318 npm tests, 24 Java tests, typechecking, builds, and Electron smoke passed. Those green checks are real, but insufficient: the current tests explicitly approve one product-contract regression and do not measure the reproduced optimizer, allocation, crash, or robot-loop failures.

Implementation update · 2026-08-09

Approved remediation implemented. LabVIEW 4.4 is preserved on the pushed archive/labview-4.4 branch and removed from main. The main application now supports only the profiled and optimized planners plus bounded Java JSON export. The owner's checked-in wine-glass platform branding was retained, and the obsolete Chap requirement was removed from main's repository invariants.
  • Fixed optimizer stop mapping, post-smoothing feasibility, measured diagnostics, stationary-action preflight, translation-priority overshoot, renderer error containment, drag coalescing, and hidden routine/graph work.

  • Shipped pinned production React, a 700 KiB eager renderer budget, an 8 MiB ASAR budget, runtime-only packaging, one locale, tag/version validation, Java integration CI, and a single app-managed Java support path.

Scope and method

This is a current-tree audit, not a replay of the July review. It inspected tracked source, tests, examples, documentation, workflows, prior plans, generated outputs, ignored releases, dependency/package contents, and Git object retention. Third-party and generated trees were inventoried and measured for dependency, package, and workspace impact; vendored library internals were not line-reviewed as first-party code.

The worktree already contained 14 modified/deleted files and three new icon assets. The audit intentionally made no application-code changes and treated those edits as the product under review. Reproductions compiled only into temporary directories.

Maintainability judgment

Keep

  • The separate static renderer compatibility math: repository rules require a browser approximation and shared compiled planner. The missing piece is differential testing, not blind deduplication.
  • The narrow production dependency set: MCP server and Zod on the desktop, Jackson plus WPILib-provided APIs on the robot.
  • The hardened Electron boundary, strict BDX scalar reader, project migrations, atomic Java support writes, symlink checks, fixed subprocess arguments, and existing focused compatibility fixtures.

Simplify

  • Make high-frequency state ownership local: geometry authoring, playhead animation, and agent publication should not share one synchronous root pipeline.
  • Split only the proven responsibility knots: the 801-line Java processor into inspection/serialization/emission; planner provenance at a typed boundary; pointer-drag cleanup into one primitive.
  • Remove confirmed dead assets/rules and package metadata through explicit allowlists. Do not launch broad framework rewrites or replace Electron without a hard product-size requirement.

Remediation sequence

  1. Release blockers: restore branding/startup invariant; fix both optimized planner defects; add stationary-action preflight; contain clothoid errors; add exact regressions.
  2. Runtime safety: bound Java follower and reader; add project/boolean limits; preflight Java/BDX export; keep heavy analysis off the Electron main thread.
  3. Interactive performance: coalesce drag state/publication; isolate playback; gate hidden work; remove idle one-second agent polling.
  4. Package diet: production React, runtime-only ASAR, English locale allowlist, production tsconfig/map exclusion, explicit package budget.
  5. Verification and ownership: behavior-based renderer tests, packaged smoke, Java integration, tag/version check, supported plugin decision, compact root architecture guide.
  6. Workspace hygiene: documented cleanup of old releases, remote branches, duplicate field image, and supported checkpoint pruning. Keep this last; it does not fix user-facing performance.

Acceptance budgets

  • Optimized output contains zero velocity only at authored stops/endpoints and independently measures no authored constraint excess beyond defined numerical tolerance.
  • Every planner/export path rejects over-budget sample counts before allocating per-sample objects; hostile waits/imports return descriptive errors, not RangeError or process exhaustion.
  • At 100 waypoints, drag work stays below a 16.7 ms p95 target on the reference machine, commits at most once per frame, and performs no more than one coalesced external publication with pointer-up flush.
  • Playback does not commit root editor state per frame and does not build a hidden graph.
  • Robot follower work per tick is bounded and benchmarked; runtime reader ceilings are demonstrated under the target roboRIO memory budget.
  • Production renderer contains no *.development.js; eager JS, ASAR, metadata, locale, and packaged-download sizes have enforced CI budgets.
  • Package workflow rejects mismatched tags and runs smoke against the packaged executable; CI runs Java integration without rebuilding the same output twice.

Limits of this review

  • No controlled command-free LabVIEW v4.4 golden fixture was available, so this review does not claim byte-identical LabVIEW parity beyond the existing proven contract.
  • The robot findings are code-path and complexity based; final ceilings and follower performance must be profiled on the target roboRIO.
  • The renderer timing probe is synthetic and local. It establishes risk and a baseline, not a universal device benchmark.
  • Ignored release artifacts were generated at several dates. Their contents were used for payload/workspace accounting, not as proof of one coherent release build.
Bottom line: Bordeaux does not need a rewrite. The lightest maintainable path is to fix the five correctness/resource boundaries, localize high-frequency UI state, stream/bound robot work, and make packaging explicit. The existing security, compatibility structure, and small dependency surface are worth preserving.

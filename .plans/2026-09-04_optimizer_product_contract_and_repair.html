Confirmed owner decisions

  • Optimization may change geometry only inside a corridor the owner controls, preserving required waypoints and headings.
  • Draw with a fast normal preview, explicitly optimize, compare, then apply.
  • Target about five seconds for a normal optimization run, with a deeper option.
  • Select optimization per path, and provide Optimize all for final preparation.
  • Reported regression: switching to the optimizer briefly shows a 3.7-second path, then switches back to the profiled result. The owner confirmed it reverts while completely idle, without any further editing or interaction.

Product contract

A team can draw a path, set its robot and constraints, inspect playback, and export a validated normal trajectory without choosing an optimizer. Sharing sound physics between normal and optimized generation is desirable. Do not weaken normal mode to manufacture a speedup.

Optimization searches for a faster valid trajectory using the freedom the team explicitly grants. The drawn path remains the editable source. Preserve waypoint requirements, active heading laws and priority semantics, stops, waits, markers, route topology, field clearance, and drivetrain limits. Show the allowed corridor before search, with a distance in the current units; increasing it must be deliberate. Define it against the authored route and swept robot footprint consistently with validation. Never widen it automatically or move required constraints to obtain a result.

The initial proposed objective is minimum total execution time, including required stationary actions and heading completion, under the same constraints as the normal baseline. Tracking quality and smoothness need measurable criteria and robot evidence before claims are made. No promise of globally optimal motion or improvement on every route.

What the review found

  • The UI replaces its displayed result with the interactive preview after edits, then swaps in the final result. A failed final request retains the preview.
  • Normal and optimized generation already share physics-aware fixed-path timing. The optional gain largely depends on searching geometry.
  • The default corridor optimizer evaluates one geometry candidate; its local search cannot run at that budget.
  • Candidate rejection reasons are discarded, and time limits terminate the worker without delivering a best-so-far candidate.
  • Path view, routine planning, and export generate independently. A redesign must give all three the same accepted result identity.

Evidence and limitations are in the companion review. Findings are tracked as #156 (default search), #157 (result ownership), #158 (timeout/incumbent), #159 (honest outcomes), and #160 (baseline validation). This extends the existing Bordeaux Planner Math Repair work; it does not replace the locally verified heading-priority changes tracked in issue #143.

Approved user experience

  1. Draw. Pointer edits use a lightweight preview. Once settled, normal generation validates the current path. Loading and invalid input are explicit; a coarse preview is never presented as export-ready evidence.
  2. Optimize. Start from the current validated baseline. Show elapsed time, validated candidates considered, best gain found, and Cancel. Avoid fictional percentage progress. The current accepted trajectory remains selected while search runs.
  3. Compare. Show normal and candidate total time, seconds and percentage saved, geometric deviation, and limiting constraints. Use an explicit baseline/candidate toggle or overlay. Starting playback uses one immutable trajectory; background work does not change its duration or pose mid-run.
  4. Apply or keep normal. Apply selects the validated candidate for playback, routine use, and export. Keep normal remains a first-class choice. Search completion alone does not change the selected result under the confirmed explicit workflow.
  5. Edit again. A trajectory-affecting edit marks the prior optimization stale. Show the current drawing preview and regenerate its normal baseline. Preserve the older candidate only as labeled history; it cannot masquerade as current or be exported for changed inputs. Selection, zoom, and panel changes must not invalidate optimization.
  6. Prepare an autonomous routine. Optimize all queues paths with bounded concurrency, reports each outcome, and preserves already accepted paths. No hidden re-optimization on export.

One result contract

Track result quality separately from why search stopped: an improved or unchanged valid result can coexist with completed, work-budget-exhausted, canceled, or timed-out termination. Exhausting a budget does not discard an improvement or establish optimality. The table describes user-facing situations, not mutually exclusive solver enum values.

State/outcomeMeaning and behavior
Normal readyThe current baseline passed the authoritative validation pipeline. It is usable with optimization off.
SearchingA job tied to current input identity is exploring. Keep accepted geometry, graphs, and playback stable.
ImprovedA candidate is validated and exceeds the material-gain threshold. It is available to compare and apply.
No material gainThe search found no meaningful improvement; report its termination reason and whether any alternative candidate passed validation. Keep normal; do not call it a failure or proof of optimality.
Search exhaustedThe requested work budget was used. Report the best valid result and whether any candidate passed validation.
UnsupportedThe chosen search cannot alter this geometry/action type. Explain the specific limitation and retain a valid normal trajectory.
Invalid baselineNormal generation itself cannot meet the authored constraints. Identify the failing constraint/location; never claim search failure proves mathematical infeasibility.
Canceled / failedPreserve the selected current result. A separately delivered, validated incumbent may remain available for comparison. Internal errors remain diagnosable.
StaleInputs changed. Do not apply or export the old candidate as current.

Store baseline, candidate, and selected-result identity separately. Tie each result to all trajectory-affecting inputs: path geometry and actions, effective robot limits, field/clearance model, planner version, and optimization options. Ignore late messages for old jobs. Start with one small owner for this state; avoid another competing cache or generic job framework.

Implementation sequence and review gates

  1. Reproduce and freeze evidence. Capture the confirmed idle reproduction: enable optimization, observe the 3.7-second result, make no further input, and wait for reversion. Obtain that path and trace the responsible worker/status transition; preserve the current dirty work. Add behavior tests for optimized → edit → preview → result, switching paths, changing robot limits, cancellation, and old replies. Record default/deep performance on the same corpus and constraints. Success: the reported idle switching is explained by an observed trace, not just inferred from source. A completed accepted result must remain selected indefinitely without input; a provisional result must be visibly labeled and must never look like an accepted optimization.
  2. Make the baseline authoritative. Reuse the shared physics-aware pipeline; require every returned usable baseline to pass validation and retain real diagnostics. Reduce duplicate wrapper work only where proven equivalent. Preserve issue #143 behavior. Main areas: shared planner index, fixedGeometryFinal, trajectoryValidation, worker conversion. Success: ordinary supported fixtures are valid and no fallback can claim zero violations without evidence.
  3. Fix result ownership and explicit workflow. Implement the baseline/candidate/selected model in App and final-planning transport, with compare/apply and stale rules. Worker progress is informational until a validated candidate is ready. Main areas: App, Panels, FieldView, final-planning, preview worker. Success: no background replacement of selected playback; meaningful edits invalidate precisely once.
  4. Make search worthwhile. Replace the single default probe with measured deterministic search effort. First improve existing handle-length exploration: feasible step sizes, reuse baseline work, and retain the best validated candidate. Add bounded rejection counts and representative causes. Cooperative checkpoints must reserve time to return the incumbent before hard worker termination. A deeper effort uses a deterministic continuation of the same search; hard safety timeout remains distinct from work quality. Expand to handle directions or joint heading choices only if the owner grants freedom and benchmarks show the simpler search is insufficient.
  5. Unify saved selection, routines, and export. Add a backward-compatible per-path optimization selection and options representation, retaining a documented migration for legacy project-wide plannerId. Persist the selected validated artifact with its input/version identity, or define an equivalent reproducibility contract before implementation. Invalidate mismatches on reopen. BDX export and Java runtime must consume the selected trajectory without a fresh, potentially different optimization. Legacy plannerId files must still load predictably. Inspect shared types, project normalization/file format, BDX, routine planning, and Java reader tests.
  6. Prove value and review independently. Run the agreed corpus and interaction tests, then real-robot trials when tracking claims are in scope. A separate read-only review checks correctness, scope, maintainability, and product behavior before shipping. Publish results against each acceptance criterion, including routes that do not improve.
